# 인증(로그인) API 명세 및 설계 기록

> BE/login 브랜치에서 도입된 세션+쿠키 기반 인증의 명세와 설계 결정 기록.
> 라이브 문서는 서버 기동 후 `http://localhost:9090/swagger-ui.html` 의 **Auth / Me** 태그 참조.

## 1. 인증 방식 개요

**세션 + HttpOnly 쿠키** 방식이다. 토큰(JWT)을 클라이언트에 저장하지 않는다.

```
로그인 성공
  → 서버가 인증 정보를 HTTP 세션에 저장
  → 응답에 Set-Cookie: JSESSIONID=...; HttpOnly
  → 이후 브라우저가 쿠키를 자동 전송 → 서버가 세션에서 사용자 식별
```

- 쿠키가 `HttpOnly`라 자바스크립트로 탈취 불가(XSS 방어).
- 프론트는 same-origin(개발: Vite proxy `/api`→9090)이므로 별도 CORS credentials 설정 없이 쿠키가 오간다.
- 로그인 여부 확인은 클라이언트가 저장한 값이 아니라 **`GET /api/me` 호출 결과**로 판단한다.

## 2. 엔드포인트

| Method | URL | 인가 | 성공 응답 | 주요 실패 |
|---|---|---|---|---|
| POST | `/api/auth/signup` | 공개 | **201** MeResponse | 400 `invalid-request`, 409 `duplicate-username` / `duplicate-email` |
| POST | `/api/auth/login` | 공개 | **200** MeResponse + 세션 쿠키 | 401 `bad-credentials` |
| POST | `/api/auth/logout` | 공개(멱등) | **204** (빈 본문) | — |
| GET | `/api/me` | **인증 필요** | **200** MeResponse | 401 `unauthenticated` |

### 요청/응답 형식

**SignupRequest** — `username`(3~30자) · `password`(8~100자) · `nickname`(2~30자) · `email`(이메일 형식)

**LoginRequest** — `username` · `password`

**MeResponse** (signup/login/me 공통 응답)
```json
{
  "id": 1,
  "username": "prompter01",
  "nickname": "프롬프터",
  "email": "prompter@example.com",
  "createdAt": "2026-07-29T05:00:00Z"
}
```
비밀번호 해시는 어떤 응답에도 포함되지 않는다.

### 동작 세부

- **signup은 세션을 만들지 않는다.** 가입 후 로그인 상태가 되려면 클라이언트가 이어서 `POST /api/auth/login`을 호출한다(프론트 SignupPage가 이렇게 동작).
- **login 응답 본문이 곧 사용자 정보**라 로그인 직후 `/api/me`를 또 호출할 필요 없다.
- **logout이 204(No Content)인 이유**: 프론트 공용 apiClient가 204만 빈 본문으로 처리하기 때문. 또한 세션이 없어도 204를 반환하는 멱등 동작이라, 세션 만료 후 로그아웃을 눌러도 에러가 나지 않는다.
- **로그인 실패는 아이디 없음/비밀번호 불일치를 구분하지 않고** 동일한 401 `bad-credentials`("아이디 또는 비밀번호가 올바르지 않습니다.")를 반환한다 — 계정 존재 여부 노출(계정 열거 공격) 방지.

## 3. 에러 코드표 (기존 `{code, message}` 포맷 유지)

| HTTP | code | 언제 |
|---|---|---|
| 400 | `invalid-request` | @Valid 검증 실패(형식·길이) |
| 401 | `bad-credentials` | 로그인 실패 |
| 401 | `unauthenticated` | 비로그인으로 보호 API 접근 (Security 필터가 컨트롤러 진입 전 차단) |
| 403 | `access-denied` | 인증됐으나 권한 부족 (현재는 권한 등급이 하나라 사실상 미발생) |
| 409 | `duplicate-username` | 아이디 중복 |
| 409 | `duplicate-email` | 이메일 중복 |
| 409 | `duplicate-user` | 동시 가입 레이스에서 DB UNIQUE 제약에 걸린 경우(안전망) |

⚠️ **프론트 파싱 한계(현황 유지 결정)**: 프론트 apiClient는 RFC7807(`detail`)을 기대해 이 `{code,message}`의 message를 화면에 전달하지 못한다. 그래서 프론트 로그인/가입 폼은 **HTTP 상태코드로 분기**해 한국어 문구를 자체 표기한다(401→"아이디 또는 비밀번호가...", 409→"이미 사용 중인 아이디 또는 이메일입니다."). 409에서 아이디/이메일 중복을 구분할 수 없는 것도 이 한계 때문이다. 에러 포맷 통일은 후속 과제(§6).

## 4. DB

`schema.sql`에 멱등 DDL로 추가(기존 방식 그대로, Flyway 미사용):

```sql
CREATE TABLE IF NOT EXISTS users (
    id            BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    username      VARCHAR(30)              NOT NULL,
    password_hash VARCHAR(100)             NOT NULL,   -- BCrypt 해시만 저장(평문 금지)
    nickname      VARCHAR(30)              NOT NULL,
    email         VARCHAR(255)             NOT NULL,
    created_at    TIMESTAMP WITH TIME ZONE NOT NULL
);
CREATE UNIQUE INDEX IF NOT EXISTS uq_users_username ON users (username);
CREATE UNIQUE INDEX IF NOT EXISTS uq_users_email ON users (email);
```

- 테이블명이 단수형 관례와 달리 `users`인 것은 `user`가 PostgreSQL 예약어이기 때문.
- 서비스 계층 중복 검사 + DB UNIQUE 제약의 이중 방어.
- 테스트: `support/DatabaseTest`의 TRUNCATE 목록에 `users` 포함됨.

## 5. 보안 설계 결정 기록

| 결정 | 내용 | 근거 |
|---|---|---|
| 인가 정책 | `/api/me/**`만 인증 필요, **나머지 전부 공개**(`anyRequest().permitAll()`) | 이번 범위는 "로그인만" — 기존 문제/어템프트 API는 비로그인 유지. 공개 경로 열거 방식은 /error·swagger 누락 위험 |
| 사용자 식별 | 컨트롤러는 `@AuthenticationPrincipal`(세션)에서만 사용자 ID를 얻음. URL·바디로 userId를 받지 않음 | 클라이언트 식별자 위조 방지 (IDOR 차단). `/api/users/{id}`가 아닌 `/api/me`인 이유 |
| 비밀번호 | BCrypt 해시 저장. 엔티티 필드명도 `passwordHash` | 평문 저장 원천 차단 |
| **CSRF 비활성** | `csrf.disable()` (SecurityConfig에 주석으로 근거 명기) | 현재 인증 필요한 상태 변경 API가 없어 보호 대상이 로그인 세션뿐. 켜면 기존 비인증 POST(어템프트) 테스트 전부와 프론트 공용 apiClient 수정 필요. **어템프트 소유자 도입 시 CookieCsrfTokenRepository로 활성화** — 방법은 `login-sandbox` LEARNING.md에 검증·기록됨 |
| 세션 저장소 | 톰캣 기본 인메모리 | 단일 인스턴스 배포 전제(FeedbackGenerationGuard와 동일). 다중 인스턴스 시 spring-session-data-redis (인프라에 Redis 이미 존재) |
| CORS | 기존 컨트롤러별 `@CrossOrigin(origins="http://localhost:5173")` 관례 유지 + Security `.cors(withDefaults())` | 개발·운영 모두 proxy 기반 same-origin 전제. cross-origin 배포 시 전역 CORS + allowCredentials로 전환 필요(§6) |

## 6. 후속 과제

1. **어템프트 소유자**: `attempt.user_id` 추가 + "내가 푼 문제" 조회 (`GET /api/me/attempts`) — 패턴은 login-sandbox에서 검증 완료. 이때 **CSRF 활성화 필수**.
2. **마이페이지 통계 API**: SOLVED/SUBMISSIONS/STREAK — 현재 프론트 MyPage는 더미 표시.
3. **에러 포맷 통일**: 백엔드 `{code,message}` vs 프론트 RFC7807 파서 — 팀 결정 필요. 통일되면 서버 메시지를 화면에 그대로 노출 가능.
4. **운영 same-origin 확보**: 프론트 nginx.conf에 `/api` 프록시가 없음. 운영에서 FE/BE 오리진이 다르면 세션 쿠키가 전송되지 않는다 → nginx `location /api { proxy_pass ...; }` 추가 또는 전역 CORS+credentials 전환.
5. **세션 Redis 전환**: 다중 인스턴스 배포 시.

## 7. 수동 검증 (curl)

```bash
B=http://localhost:9090

# 가입 (201)
curl -i -X POST $B/api/auth/signup -H "Content-Type: application/json" \
  -d '{"username":"alice","password":"password123","nickname":"앨리스","email":"alice@example.com"}'

# 로그인 → Set-Cookie: JSESSIONID=...; HttpOnly 확인 (200)
curl -i -c cookies.txt -X POST $B/api/auth/login -H "Content-Type: application/json" \
  -d '{"username":"alice","password":"password123"}'

# 내 정보 (쿠키 포함, 200)
curl -b cookies.txt $B/api/me

# 비로그인 me (401 unauthenticated)
curl -i $B/api/me

# 로그아웃 (204) 후 me (401)
curl -b cookies.txt -X POST $B/api/auth/logout -i
curl -b cookies.txt $B/api/me
```

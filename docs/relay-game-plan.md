# 릴레이 게임 (WebRTC) 구현 계획

여러 사람이 하나의 문제를 순서대로 이어 푸는 게임 모드. 기존 문제 풀이 흐름은 그대로 두고
별도 도메인(`relay`)으로 붙인다.

## 게임 규칙

1. 방이 하나 존재하고 여러 사용자가 입장한다. **입장한 사람은 곧 참가자다** — 방을 구경하는
   상태는 없다. 방을 만든 사람도 개설과 동시에 첫 번째 참가자가 되므로 1번 좌석은 항상 방장이다.
2. 풀이 순서는 **입장 순서** 그대로. 순서 변경 기능은 범위 밖.
3. **방장이 시작 버튼**을 누르면 입장이 마감되고 순서가 확정된다.
4. 정해진 순서대로 프롬프트를 입력해 결과 코드를 받는다. **정해진 바퀴 수만큼 순환**한다.
5. **한 사람의 순서가 끝나면 빌드/테스트가 자동으로 요청되고, 그 결과를 전원이 확인한다.**
   다음 주자는 통과 현황을 보고 자기 턴을 시작한다.
6. 마지막 바퀴 마지막 주자의 채점까지 끝나면 전원이 피드백 페이지로 이동해 피드백을 확인한다.

총 턴 수 = 참가자 수 × 바퀴 수. 참가자 수가 시작 시점에 확정되므로 총 턴 수도 그때 확정된다.

매 턴 채점은 두 가지를 얻는다. 다음 주자가 **현재 통과 현황을 알고 시작**하므로 릴레이에 전략이
생기고, 직전 턴 대비 통과 증가분이 그 주자의 **기여도 점수**가 된다.

## 설계 원칙

### 1. 두 레이어를 섞지 않는다

| 레이어 | 전송 | 내용 | 유실 시 |
| --- | --- | --- | --- |
| 게임 상태 | **WebSocket** (서버 권위) | 턴 순서, 현재 코드, 진행 단계, 채점·피드백 결과 | 재접속 시 서버에서 전체 스냅샷 재조회 |
| 사람 레이어 | **WebRTC** | 음성/영상, 타이핑 미리보기, 리액션 | 무해 — 게임 진행과 무관 |

게임 상태를 P2P로 동기화하면 "누구 화면이 진실인가" 문제가 반드시 터진다. LLM 호출과 채점이
서버에서만 일어나므로 서버가 유일한 진실의 원천이어야 한다.

WebRTC는 장식이 아니다. 릴레이의 재미는 대기 중인 사람들이 훈수를 두는 데서 나오고, 그건
음성이 있어야만 성립한다. 특히 종료 시퀀스(1~2분 대기)에서 값어치를 한다.

### 2. 게임 도메인은 분리하되, 코드 진화 인프라는 재사용한다 (사이드카)

`relay` 패키지와 `relay_*` 테이블은 전부 새로 만든다. 다만 **방 하나 = 어템프트 하나**로 두고
프롬프트·코드·파일 변경·채점은 기존 어템프트 인프라를 그대로 쓴다.

인가를 두 층으로 나누는 것이 핵심이다.

- **"지금 네 순서인가"** → 릴레이 도메인이 판정한다.
- 판정을 통과하면 릴레이 서비스가 **방장 신원으로** `AttemptService.addTurn`을 호출한다.

어템프트 입장에서는 평범한 자기 소유 어템프트일 뿐이라 기존 코드가 그대로 동작한다.
`CodeGenerationGuard`의 어템프트당 직렬화, 멱등 처리, `code_run`의 FK, 파일 재생(`FileReplay`)이
전부 공짜로 따라온다.

**대가**: 릴레이가 나중에 근본적으로 다른 규칙(턴 롤백, 분기 등)을 원하면 그때 분리 비용을 낸다.
지금 규칙은 "턴을 순서대로 쌓는다"뿐이라 어템프트와 정확히 같은 모양이다.

### 3. 피드백은 이미 구현되어 있다

`Attempt.submit`이 `turnFeedbacks.size() != turns.size()`를 검증하고 턴마다 피드백을 배정한다
(`Attempt.java:104-112`). 릴레이는 턴 i의 작성자를 알고 있으므로, 기존 피드백 생성기가 손대지
않은 채로 **주자별 프롬프트와 그에 대한 피드백**을 내놓는다. 바퀴가 여러 번이면 한 사람이
여러 개를 받아서 "바퀴마다 프롬프트가 나아졌는가"까지 보인다.

## 스키마

```sql
-- 릴레이 게임 방 하나. 코드 진화는 attempt_id가 가리키는 어템프트가 담당한다.
CREATE TABLE IF NOT EXISTS relay_room (
    id                BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    problem_id        BIGINT      NOT NULL REFERENCES problem (id),
    host_user_id      BIGINT      NOT NULL REFERENCES users (id),
    -- 시작 시점에 만든다. WAITING 동안은 NULL이다.
    attempt_id        BIGINT      REFERENCES attempt (id),
    status            VARCHAR(30) NOT NULL,
    total_laps        INT         NOT NULL,
    max_participants  INT         NOT NULL,
    -- 시작 시 확정한 참가자 수. 이후 이탈해도 좌석 수는 변하지 않는다.
    seat_count        INT,
    -- 릴레이 진행 인덱스. 좌석과 바퀴를 여기서 파생한다(아래 설명).
    current_turn_index INT        NOT NULL DEFAULT 0,
    turn_deadline     TIMESTAMP WITH TIME ZONE,
    -- 진행 중인 채점 run. 워커 결과 이벤트를 이 값으로 방에 되돌려 잇는다.
    current_run_id    UUID,
    created_at        TIMESTAMP WITH TIME ZONE NOT NULL,
    started_at        TIMESTAMP WITH TIME ZONE,
    finished_at       TIMESTAMP WITH TIME ZONE
);

-- 방 참가자. seat_order는 시작 시점에 joined_at 순으로 부여한다.
CREATE TABLE IF NOT EXISTS relay_participant (
    id         BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    room_id    BIGINT NOT NULL REFERENCES relay_room (id) ON DELETE CASCADE,
    user_id    BIGINT NOT NULL REFERENCES users (id),
    seat_order INT,
    joined_at  TIMESTAMP WITH TIME ZONE NOT NULL,
    left_at    TIMESTAMP WITH TIME ZONE
);
-- 같은 사람이 두 번 입장할 수 없고, 좌석 번호도 겹칠 수 없다. 동시 입장 레이스를 DB가 막는다.
CREATE UNIQUE INDEX IF NOT EXISTS uq_relay_participant_user ON relay_participant (room_id, user_id);
CREATE UNIQUE INDEX IF NOT EXISTS uq_relay_participant_seat ON relay_participant (room_id, seat_order)
    WHERE seat_order IS NOT NULL;

-- "몇 번째 턴을 누가 썼는가"만 기록하는 사이드카. 프롬프트와 코드는 attempt_turn에 있다.
CREATE TABLE IF NOT EXISTS relay_turn (
    id                  BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    room_id             BIGINT NOT NULL REFERENCES relay_room (id) ON DELETE CASCADE,
    -- 릴레이 진행 인덱스. 0-based이고 스킵된 턴도 번호를 차지한다.
    turn_index          INT    NOT NULL,
    author_user_id      BIGINT NOT NULL REFERENCES users (id),
    -- 대응하는 attempt_turn.ordinal. 스킵(타임아웃·이탈)이면 NULL이다.
    -- 스킵이 생기면 turn_index와 어긋나므로 둘을 따로 들고 있어야 한다.
    attempt_turn_ordinal INT,
    -- 이 턴 직후의 채점. 결과는 code_run/code_run_case에 있고 여기엔 참조와 집계만 둔다.
    run_id              UUID,
    -- 채점 집계 스냅샷. code_run_case를 세면 나오는 값이지만, 점수는 "직전 턴 대비 증가분"이라
    -- 턴마다 확정된 값이 남아 있어야 계산이 안정적이다.
    passed_count        INT,
    total_count         INT,
    started_at          TIMESTAMP WITH TIME ZONE NOT NULL,
    finished_at         TIMESTAMP WITH TIME ZONE
);
CREATE UNIQUE INDEX IF NOT EXISTS uq_relay_turn_index ON relay_turn (room_id, turn_index);
```

### 점수는 통과 증가분에서 파생한다

`passed_count`가 턴마다 남으므로 주자의 기여도는 `이번 턴 passed - 직전 턴 passed`다. 첫 턴의
기준선은 시작 시점의 스켈레톤 채점 결과다(아래 "베이스라인 채점" 참고).

증가분이 음수일 수 있다 — 앞사람이 통과시킨 테스트를 깨뜨리는 프롬프트를 쓴 경우다. 이걸 0으로
깎지 않는 편이 게임으로서 낫다. 릴레이에서 남의 코드를 망가뜨리는 건 실제로 일어나는 실패이고,
그게 드러나는 것이 이 게임의 재미다.

### 좌석과 바퀴는 단일 카운터에서 파생한다

`current_turn_index` 하나로 충분하다.

```
좌석    = current_turn_index % seat_count
바퀴    = current_turn_index / seat_count
종료 조건 = current_turn_index == seat_count * total_laps
```

좌석과 바퀴를 따로 저장하면 둘이 어긋날 수 있다. 파생은 한 곳에서만 한다
(`AttemptView.reconstruct`가 현재 파일을 파생하는 것과 같은 판단).

### 턴 순서 레이스는 조건부 UPDATE로 막는다

"내 순서인가" 검사 후 LLM 생성이 수십 초 걸린다. 그 사이 같은 사람이 두 번 누르거나 다음 사람이
새치기할 수 있다. `CodeGenerationGuard`가 어템프트당 하나로 막아주지만, 좌석 단위로 명확히 막는다.

```sql
UPDATE relay_room SET status = 'TURN_GENERATING'
WHERE id = ? AND current_turn_index = ? AND status = 'PLAYING'
```

영향 행이 0이면 요청을 거절한다. `uq_code_run_active` 부분 유니크 인덱스와 같은 철학 — 레이스를
애플리케이션 락이 아니라 DB가 막는다.

## 상태 머신

```
WAITING
  └─(방장 시작: 좌석 확정 + 어템프트 생성 + 베이스라인 채점)→ PLAYING
                                                                │
       ┌────────────────────────────────────────────────────────┤
       │                                                        ↓
       │                                             TURN_GENERATING
       │                                          (프롬프트 → LLM 코드 생성)
       │                                                        ↓
       │                                               TURN_GRADING
       │                                        (자동 채점 요청 → 워커 왕복)
       │                                                        │
       ├──(턴 남음: 결과 브로드캐스트 후 좌석 전진)─────────────┤
       │                                                        │
       │                                              (마지막 턴이었음)
       │                                                        ↓
       │                                            FEEDBACK_GENERATING
       │                                                        ↓
       │                                                    FINISHED
       │
       └─(생성 실패)→ 방에 알리고 PLAYING 복귀 (같은 좌석 재시도)
```

**마지막 턴이 특별 케이스가 아니다.** 모든 턴이 `생성 → 채점`을 똑같이 거치고, 마지막 턴이었을
때만 그 뒤에 피드백 생성이 한 단계 붙는다. 채점 결과 핸들러가 "마지막 턴이었나"만 분기하면 된다.

### 턴 사이클은 2단 비동기 체인이다

| 단계 | 상태 | 소요 | 성격 |
| --- | --- | --- | --- |
| 코드 생성 | `TURN_GENERATING` | 수십 초 | 동기 (LLM 툴 루프, 최대 5분 예산) |
| 빌드/테스트 채점 | `TURN_GRADING` | 수십 초 | 비동기 (RabbitMQ 왕복) |
| (마지막 턴만) 피드백 생성 | `FEEDBACK_GENERATING` | 수십 초 | 동기 (LLM) |

**채점을 기다린 뒤 좌석을 전진시킨다.** 채점을 백그라운드로 돌리고 다음 턴을 바로 시작하면
페이스는 빠르지만, 결과가 뒤늦게 도착해 "지금 보이는 통과 수가 누구 턴 것인지" 헷갈린다.
다음 주자가 현재 통과 현황을 보고 시작하는 것이 이 규칙의 목적이므로 기다리는 쪽이 맞다.

**대가는 페이스다.** 턴 하나가 1분 가까이 걸리므로 5명 2바퀴면 10분을 넘긴다. 대기 시간에
음성으로 떠드는 것이 컨셉이라 치명적이지는 않지만, 바퀴 수 기본값을 정할 때 이 계산을 염두에 둔다.
진행 단계를 촘촘히 브로드캐스트해서 "멈춘 것처럼 보이는" 구간을 없애는 것이 중요하다.

**채점 완료를 릴레이가 받는 방법.** 결과는 `CodeRunResultListener` → `CodeRunService.applyResult`로
들어온다. `applyResult`에서 `CodeRunFinishedEvent(runId, status)`를 발행하고 릴레이가
`@TransactionalEventListener(AFTER_COMMIT)`으로 구독한다. 릴레이는 `relay_room.current_run_id`로 방을
찾으므로 이벤트에 어템프트 정보가 필요 없고, `CodeRunResult`가 이미 들고 있는 값만 실으면 된다.
릴레이 방이 없는 일반 어템프트 run이면 리스너가 조회에 실패하고 그냥 무시한다.

**피드백 생성을 리스너 스레드에서 하면 안 된다.** `AttemptService.submit`은 LLM 호출로 수십 초
블로킹인데, RabbitMQ 리스너 컨테이너 스레드에서 돌리면 그 시간 동안 다른 채점 결과가 밀린다.
별도 executor로 넘긴다.

**채점이 실패해도 게임을 멈추지 않는다.** 해당 턴의 `passed_count`를 NULL로 남기고 "채점 실패"를
표시한 채 좌석을 전진시킨다. 마지막 턴이었다면 그대로 피드백 생성으로 넘어간다 — 피드백은 턴
기록으로 만들고 채점 결과에 의존하지 않는다.

이게 매 턴 채점에서 특히 중요하다. `CodeRunService.STALE_RUN_TTL`이 2분이라 채점이 그보다 오래
걸리면 `expireStale`이 `RUNNER_ERROR`로 회수하는데, 턴이 N배 많아지면 이 타임아웃을 만날 확률도
N배가 된다. 한 번의 채점 실패로 게임 전체가 무너지지 않게 해야 한다.

### 베이스라인 채점

첫 주자의 기여도를 계산하려면 스켈레톤 상태의 통과 수가 필요하다. `requestRun`은 턴이 없으면
시작 스켈레톤을 실행하므로(`CodeRunService.java:65-71`) 시작 버튼 처리에 채점 한 번을 끼우면 된다.

대가는 시작이 수십 초 느려지는 것이다. 생략하고 첫 주자의 기준선을 0으로 두는 선택도 가능하지만,
스켈레톤이 이미 통과시키는 테스트가 있으면 첫 주자 점수가 부풀려진다.

### 이탈과 타임아웃

- **시작 전 이탈**: `seat_order`는 시작 시점에 부여하므로 재정렬할 것이 없다. 행만 지운다.
- **방장의 시작 전 이탈**: 남은 참가자 중 가장 먼저 입장한 사람에게 시작 권한을 넘긴다.
  방장도 참가자이므로 나갈 수 있고, 넘기지 않으면 나간 사람의 ID가 남아 아무도 시작할 수 없는
  방이 된다. 아무도 남지 않았으면 그대로 둔다 — 빈 방은 시작할 사람도 없으므로 해가 없다.
- **시작 후 이탈**: 좌석을 유지한다. 그 좌석의 턴이 오면 제한시간까지 기다렸다 스킵한다.
- **스킵의 부수 효과**: 스킵된 턴은 `attempt_turn`에 생기지 않으므로 `Attempt.submit`의
  피드백 개수 검증이 자동으로 맞아떨어진다. 별도 처리가 필요 없다.
- **스킵된 턴은 채점하지 않는다**: 코드가 그대로이므로 채점할 것이 없다. 직전 결과를 유지하고
  `TURN_GRADING`을 건너뛰어 바로 좌석을 전진시킨다.
- **생성 중 이탈**: 서버 작업이 이미 진행 중이므로 그 턴은 성립시킨다. 좌석은 정상 전진한다.
- **타임아웃 전진**: `turn_deadline`을 두고 스케줄러가 만료된 방의 좌석을 넘긴다.

| `POST` | `/api/relay/rooms` | 방 생성 (problemId, totalLaps, maxParticipants) |
| `GET` | `/api/relay/rooms/{id}` | 방 전체 스냅샷 — 재접속 복구용 |
| `POST` | `/api/relay/rooms/{id}/participants` | 입장 |
| `DELETE` | `/api/relay/rooms/{id}/participants/me` | 퇴장 |
| `POST` | `/api/relay/rooms/{id}/start` | 시작 (방장만) |
| `POST` | `/api/relay/rooms/{id}/turns` | 프롬프트 전송 (현재 좌석만). 202 접수 후 WS로 진행 |
| `GET` | `/api/relay/rooms/{id}/code` | 현재 코드 (참가자 인가) |
| `GET` | `/api/relay/rooms/{id}/runs` | 턴별 채점 이력 — 전원이 통과 현황 확인 |
| `GET` | `/api/relay/rooms/{id}/feedback` | 종료 후 피드백 (참가자 인가) |

이 조회들을 릴레이 전용으로 두는 이유: 기존 `GET /attempts/{id}/...`는 소유자(방장)만 읽을 수 있다.
릴레이 엔드포인트가 **참가자 인가**로 확인한 뒤 내부적으로 방장 신원(`AttemptOwner.user(hostUserId)`)
으로 조회해 내려준다. 기존 엔드포인트와 서비스는 그대로 둔다 —
`CodeRunService.getRuns(attemptId, owner)`를 그대로 쓸 수 있다.

### WebSocket `/ws/relay/{roomId}`

서버 → 클라이언트

- `room.state` — 접속 직후 전체 스냅샷
- `participant.joined` / `participant.left`
- `game.started` — 확정된 좌석 순서
- `turn.started` — 좌석, 바퀴, 작성자, 마감 시각
- `turn.generating` / `turn.finished` — 코드 요약과 변경 파일
- `turn.failed`
- `grading.started` — 자동 채점 요청됨
- `grading.finished` — 통과/전체 개수, 실패한 케이스, **직전 턴 대비 증가분**
- `turn.advanced` — 다음 좌석으로 전진
- `feedback.generating` / `feedback.ready` — 전원 피드백 페이지로 이동
- `signal.*` — WebRTC 시그널링 중계 (서버는 내용을 해석하지 않는다)

클라이언트 → 서버

- `signal.offer` / `signal.answer` / `signal.ice` — 같은 방 참가자에게 중계

턴 진행은 REST로 보내고 결과를 WS로 받는다. WS를 명령 채널로 쓰지 않는다 — 인증·멱등·에러 응답을
이미 갖춘 REST 경로를 재발명하지 않기 위해서다.

## WebRTC

- **토폴로지**: mesh (각자 N-1 연결). 방 정원을 6명으로 제한하면 mesh로 끝낼 수 있다.
  8명을 넘기면 업링크가 포화되어 SFU가 필요하다.
- **시그널링**: 게임 상태와 같은 WebSocket을 쓴다. 방 참가자 목록이 이미 서버에 있으므로 중계는
  불투명한 페이로드를 참가자에게 전달하는 것뿐이다.
- **coturn 필수**: 모바일 NAT·사내망에서 P2P 직결 실패율이 무시할 수 없다. `docker-compose.yml`에
  추가한다. STUN만으로 버티면 시연 날 화면이 안 뜬다.
- **DataChannel**: 현재 주자의 **프롬프트 타이핑 미리보기**와 이모지 리액션. 초당 수십 이벤트라
  서버에 저장할 가치가 없고, 유실돼도 무해하고, 긴장감은 최고인 — WebRTC에 정확히 맞는 데이터다.

멀티 인스턴스로 확장하면 방 상태와 시그널링 중계에 Redis pub/sub가 필요하다. 지금은 단일
인스턴스 가정.

## 기존 코드 접점

사이드카 설계에서 기존 코드를 건드리는 곳은 셋뿐이다.

1. **`CodeRunService.applyResult`** — `CodeRunFinishedEvent` 발행 한 줄 추가.
2. **`MyAttemptService`** — 릴레이 어템프트가 방장 마이페이지에 섞인다. 세 선택지:
   `attempt`에 플래그 한 칼럼 / `me` 조회에서 `relay_room` 조인으로 제외 / 릴레이 기록으로 노출.
3. **없음** — 코드 실행은 `requestRun(Long attemptId)` 소유자 없는 오버로드가 이미 있다
   (`CodeRunService.java:67`). 피드백 생성은 `AttemptService.submit(attemptId, owner)`을 방장
   신원으로 호출한다. 워커(`buildandtest`)는 한 줄도 바꾸지 않는다 — 상관관계가 `runId`만으로
   잡히고 파일 내용을 메시지에 실어 보내기 때문이다.

`CodeGenerator` 포트 일반화(`AttemptView` → `CodeSession`)는 **지금 필요하지 않다.** 릴레이가
어템프트를 경유하므로 그대로 동작한다. 릴레이가 어템프트와 다른 프롬프트 히스토리를 원하는
순간(예: 이전 주자의 프롬프트 숨김)에 하면 되고, 그때 어댑터 하나만 바뀐다.

## 구현 순서

각 단계 끝에 화면에서 확인할 수 있는 것이 남게 자른다.

1. ~~**방과 로비**~~ — 완료. 방 생성/입장/퇴장, WebSocket 접속(참가자 전용), 스냅샷 브로드캐스트.
   방장은 개설과 동시에 첫 참가자가 되고, 시작 전 이탈 시 시작 권한이 위임된다.
2. ~~**턴 진행**~~ — 완료. 시작 버튼, 좌석 확정, 어템프트 생성, 프롬프트 전송, 코드 조회.
   조건부 UPDATE 레이스 방어 포함.
3. ~~**자동 채점**~~ — 완료. `CodeRunFinishedEvent`, 턴마다 채점 요청, 결과·증가분 브로드캐스트,
   베이스라인 채점(비동기), 채점 마감 스케줄러.
4. ~~**종료와 피드백**~~ — 완료. 마지막 턴 분기, 피드백 생성(별도 executor)·재시도,
   피드백·턴 이력 API, 마이페이지 제외.
5. ~~**WebRTC 음성/영상**~~ — 백엔드 완료. 시그널링 중계(발신자 서버 확정), 피어 프레즌스
   (peer.list/joined/left), 재접속 밀어내기, ICE 설정 엔드포인트, coturn 서비스.
   시그널링 규약과 수동 검증 절차는 docs/relay-webrtc-manual-check.md 참고.
6. ~~**DataChannel 부가 요소**~~ — 서버 몫 없음(P2P가 설계다). 타이핑 미리보기·리액션의
   메시지 규약을 정했고, aiortc로 시그널링 중계를 거쳐 실제 RTCPeerConnection +
   DataChannel이 성립하는 것까지 확인. 클라이언트 구현은 A505FE의 relay 도메인에 있다.
7. **견고성** — 턴 타임아웃 스케줄러(입력 대기 AFK), 이탈 스킵, 재접속 복구.
   채점 마감 회수는 3단계에서 이미 구현했다.

**1단계가 끝나면 5~6단계(WebRTC)를 2~4단계(게임 로직)와 병렬로 진행할 수 있다.** WebRTC가
게임 상태에 의존하지 않고 시그널링용 WebSocket만 필요하기 때문이다. 팀 작업을 나눌 자연스러운 경계다.

## 열어둔 결정

- **이전 주자의 프롬프트를 다음 주자에게 보여줄까?** 코드만 보여주고 프롬프트를 숨기면 "이 코드가
  왜 이렇게 생겼지"를 역추론해야 해서 난이도와 재미가 올라간다. 방 옵션으로 두는 것을 권한다.
  단, 채점 결과는 규칙상 전원 공개이므로 숨기는 대상은 프롬프트 텍스트뿐이다.
- ~~**베이스라인 채점을 넣을까?**~~ 결정: 넣되 **비동기로**. 시작은 기다리지 않고, 결과가 오기
  전까지 첫 턴 델타만 null이다. 베이스라인이 도는 중에 첫 턴 채점이 걸리면 run 충돌이 나는데,
  베이스라인 결과 이벤트가 도착하는 순간 재시도한다(실측: Hello World 스켈레톤이 4개 중 1개를
  이미 통과해, 기준선 없이는 첫 주자 점수가 1 부풀려졌다).
- **턴 제한시간 기본값과 바퀴 수 기본값.** 턴당 1분 가까이 걸리므로 둘의 곱이 곧 게임 길이다.
- **점수를 게임 중에 공개할까?** 통과 수는 전원 공개지만, 주자별 증가분(=점수)을 진행 중에도
  보여줄지는 별 문제다. 끝까지 숨기면 피드백 페이지의 반전이 커진다.
- **게스트 허용 여부.** `guest_session`이 있지만 재접속·신원 문제가 커서 로그인 유저만 권한다.
- **비용 상한.** 한 게임에 (참가자 × 바퀴) 회의 LLM 호출이 일어난다. `LlmCostCalculator`가 있으니
  방 단위 상한을 걸 수 있다.

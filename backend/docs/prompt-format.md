# 프롬프트 결과 형식

## 1. 형식 정의

### 1.1 첫 턴 — 6칸

여섯 칸 모두 필수다. 라벨을 줄 맨 앞에 두고 내용은 불릿으로 적는다.

```
목표
- (AI가 무엇을 하기를 원하는가)

작업 대상
- (어느 파일·클래스·메서드인가)
- (지금 무슨 일이 일어나고 있는가)

요구사항
- (충족해야 할 동작 1)
- (충족해야 할 동작 2)

제약
- (유지해야 하는 기존 동작)
- (건드리면 안 되는 범위)

완료 조건
- (무엇이 참이면 끝인가)

검증
- 수정 후 관련 테스트를 실행하고 실패하면 원인을 확인해 다시 수정할 것
- 실행할 수 없으면 실행했다고 답하지 말고, 못 한 이유와 요구사항 대조 결과를 밝힐 것
```

`검증` 칸의 두 줄은 기본 문구로 그대로 써도 된다. 나머지 칸은 과제마다 내용이 다르다.

### 1.2 조건부 칸 — `출력 형식`

결과물이 **코드 변경이 아니라** 설명·목록·표·데이터일 때만 일곱 번째 칸으로 붙인다.

```
출력 형식
- 표로 정리하고 열은 항목 / 현재 값 / 권장 값
```

코드 수정 과제에는 대부분 쓰지 않는다. 평가 기준 문서 4.5도 출력 형식은 작업에 필요한 경우에만 평가한다고 명시한다.

### 1.3 공통 규칙

**코드는 자연어와 섞지 않는다.** 코드·에러 로그·파일 내용은 백틱 블록으로 분리한다.

````
작업 대상
- src/main/java/com/promptstudio/post/service/PostService.java의 create
- 아래 입력이 그대로 저장됨

```
title = "   "
```
````

**모호한 낱말은 판정 기준 문장으로 바꿔 쓴다.** 용어 정의 칸은 두지 않는다. 정의를 별도 칸으로 빼면 정의 칸과 요구사항 칸이 갈라지고, 판정 기준이 두 번 나오면 느슨한 쪽이 채택된다.

| 쓰지 말 것 | 이렇게 |
| --- | --- |
| `빈 값이 저장되지 않게` | `trim 적용 후 빈 문자열이면 저장하지 않음` |
| `너무 긴 제목 막아줘` | `trim 후 길이가 100자를 넘으면 거부` |
| `적당히 검증해줘` | `제목 필수, 본문은 선택` |

**절차·단계 칸은 두지 않는다.** 판정은 결과로 한다 — 프롬프트 품질은 변경 파일로 판정하고, 탐색·수정 순서는 AI 소관이다. 수단 지정은 과잉지정에 해당한다. 특정 파일을 먼저 확인시키고 싶다면 작업 대상 칸에 위치를 정확히 적는 것으로 충분하다.

## 2. 칸별 지침

### 2.1 목표

- **쓸 것**: AI가 수행할 행동(수정·추가·분석·설명)과 그 결과 무엇이 달라지는가.
- **최소 요건**: 동사 하나 + 달라질 동작 하나. 한 줄이면 충분하다.
- **흔한 실패**: `이 코드 고쳐줘` — 무엇을 고칠지가 없다. `개선해줘` — 개선의 방향이 없다.

### 2.2 작업 대상

- **쓸 것**: 파일 경로·클래스·메서드, 그리고 지금 실제로 벌어지는 증상.
- **최소 요건**: 위치 한 줄 + 현재 증상 한 줄.
- **흔한 실패**: `게시글 기능에 문제가 있어` — 어느 계층인지 특정 안 됨. 증상 없이 위치만 적는 것도 절반이다. AI는 "무엇이 잘못됐는지"를 증상에서 읽는다.

### 2.3 요구사항

- **쓸 것**: 충족해야 할 동작을 항목별로. 정상 경로뿐 아니라 예외 상황도.
- **최소 요건**: 항목 하나에 판정 가능한 문장 하나. 두 조건을 `~하고`로 붙이지 않는다.
- **흔한 실패**: 모호어를 그대로 남김(1.3 표 참고). 예외 상황 누락 — 정상 입력만 적고 경계값·널·중복 요청을 안 적음.

### 2.4 제약

- **쓸 것**: 유지해야 하는 기존 동작, 수정 금지 범위, 파일 생성·삭제 제한, 민감정보 취급 조건.
- **최소 요건**: 유지할 동작 1줄 + 건드리면 안 되는 범위 1줄.
- **왜 필수인가**: 문제 명세는 실행 에이전트에 전달되지만, 사용자 의도의 범위는 명세에 없다. 어느 파일을 건드리면 안 되는지, 어떤 동작을 유지해야 하는지는 프롬프트만이 안다.
- **흔한 실패**: `필요한 부분은 전부 바꿔줘` — 범위를 AI에게 위임. 문제 명세의 제약 문장을 그대로 옮겨 적기 — 칸은 찼지만 판단이 없다.

### 2.5 완료 조건

- **쓸 것**: 무엇이 참이면 작업이 끝난 것인지. 통과해야 할 테스트, 관찰 가능한 결과.
- **최소 요건**: 판정 가능한 문장 하나. `잘 되면`은 판정이 아니다.
- **흔한 실패**: `잘 작동하게 해줘`. 요구사항을 그대로 복사해 붙임 — 완료 조건은 요구사항의 재진술이 아니라 **확인 방법**이다.

### 2.6 검증

- **쓸 것**: 수정 후 실행·재검토 요청, 실패 시 원인 분석과 재수정 요청, 실행 불가 시의 보고 의무.
- **최소 요건**: 1.1의 기본 두 줄.
- **왜 두 번째 줄이 필요한가**: 현재 우리 서비스의 실행 에이전트는 테스트를 돌릴 수 없다(툴은 `list_files`·`read_file`·`edit_file`뿐이다). 이 줄이 없으면 모델이 "테스트 통과를 확인했습니다"류의 하지 않은 일을 요약에 적을 수 있다. 사용자가 이 형식을 자기 도구(Claude Code·Cursor)로 가져가도 같은 방어가 필요하다 — 그 환경에서도 테스트 명령이 없거나 빌드가 깨지면 모델이 실행을 건너뛴다.
- **흔한 실패**: 검증 요청 자체가 없음(`수정만 해줘`). 실패했을 때 무엇을 하라는 지시가 없음.

### 2.7 출력 형식 (조건부)

- **쓸 것**: 표·목록·JSON 등 결과의 표현 규격과 필요한 필드·열.
- **발동 조건**: 결과물이 코드 변경이 아닐 때만.
- **흔한 실패**: 코드 수정 과제에 `JSON으로 반환해줘`라고 적음 — 실행 에이전트는 `edit_file`로 파일을 고치고 답변은 작업 요약으로 돌려주므로, 결과물의 표현 규격과 실행 계약이 뒤섞인다.

## 3. 실물 예시

### 3.1 상황

게시글 등록에서 제목에 공백만 입력해도 저장된다.

- 대상 코드: `src/main/java/com/promptstudio/post/service/PostService.java`의 `create`
- 관련 테스트: `src/test/java/com/promptstudio/post/service/PostServiceTest.java`

### 3.2 부족한 프롬프트

```
게시글 제목 검증 좀 고쳐줘. 빈 값 안 들어가게.
```

부족한 지점:

| 칸 | 상태 |
| --- | --- |
| 목표 | `고쳐줘`만 있고 어떤 상태로 바꿀지 없음 |
| 작업 대상 | 클래스·메서드 특정 없음, 증상(`" "`도 저장됨) 없음 |
| 요구사항 | `빈 값`의 기준 없음 — 빈 문자열만인지 공백 문자열도인지 |
| 제약 | 없음. 정상 제목 저장까지 막힐 수 있고 수정 범위가 열려 있음 |
| 완료 조건 | 없음 |
| 검증 | 없음 |

### 3.3 형식을 적용한 프롬프트

```
목표
- PostService.create에서 공백만 있는 제목이 저장되지 않도록 수정

작업 대상
- src/main/java/com/promptstudio/post/service/PostService.java의 create
- 지금은 제목에 "   "를 넣어도 게시글이 저장됨

요구사항
- 제목에 trim을 적용한 값으로 검증
- trim 결과가 빈 문자열이면 저장하지 않고 예외를 던짐
- trim 결과가 비어 있지 않으면 기존과 동일하게 저장

제약
- 정상 제목의 저장 동작은 그대로 유지
- PostService와 그 테스트 파일 밖은 수정하지 말 것
- 새 파일 생성 없이 기존 파일 안에서 해결

완료 조건
- 공백만 있는 제목이 저장되지 않고, 정상 제목은 저장되는 테스트가 모두 통과

검증
- 수정 후 관련 테스트를 실행하고 실패하면 원인을 확인해 다시 수정할 것
- 실행할 수 없으면 실행했다고 답하지 말고, 못 한 이유와 요구사항 대조 결과를 밝힐 것
```

## 4. 후속 턴 형식

첫 턴의 라벨을 그대로 쓰고 **새 라벨 `직전 결과` 하나만 추가**한다. 바뀐 칸만 적는다 — 이전 턴과 같은 내용을 다시 쓰지 않는다.

```
직전 결과
- (직전 수정본에서 확인한 사실 — 무엇이 맞았고 무엇이 어긋났는가)

요구사항
- (이번 턴에 새로 필요한 것)
```

**규칙 두 가지**

1. `직전 결과`는 매 턴 필수다. 직전 출력을 확인하지 않고 다음 요구를 얹는 것이 가장 흔한 실패다(평가 기준 4.6).
2. **직전 턴이 수정 범위를 벗어났다면 `제약`을 다시 쓴다.** AI가 매 턴 무엇을 고칠지 새로 결정하므로 범위 이탈은 턴마다 재발할 수 있다.

### 예시

```
직전 결과
- 공백 제목이 차단되는 것은 확인됨
- 그런데 PostController의 예외 처리까지 함께 바뀌어 응답 상태 코드가 500으로 변경됨

요구사항
- 제목 검증 실패 시 400으로 응답

제약
- PostController는 원래대로 되돌리고, 이번 수정은 PostService 안에서만 할 것

검증
- 수정 후 관련 테스트를 실행하고 실패하면 원인을 확인해 다시 수정할 것
- 실행할 수 없으면 실행했다고 답하지 말고, 못 한 이유와 요구사항 대조 결과를 밝힐 것
```

## 5. 평가 항목 매핑

| 형식의 칸 | 평가 항목 | 비고 |
| --- | --- | --- |
| 목표 | 4.1 작업 목표의 명확성 |  |
| 작업 대상 | 4.2 작업 대상과 맥락 |  |
| 요구사항 | 4.3 요구사항의 완전성 | 모호어의 판정 기준화도 여기 |
| 제약 | 4.4 수정 범위와 제약 조건 | 민감정보·파일 생성 제한 포함 |
| 완료 조건 | 4.5 결과 형식과 완료 조건 (완료 조건 부분) |  |
| 출력 형식 (조건부) | 4.5 결과 형식과 완료 조건 (형식 부분) | 코드 변경이 아닐 때만 |
| 검증 | 4.6 결과 검증과 개선 요청 |  |
| 직전 결과 (후속 턴) | 4.6 결과 검증과 개선 요청 + 4.2 맥락 |  |
| 형식 전체 | 4.7 구조와 가독성 | 칸 분리·코드 블록 분리로 충족 |

피드백에서 `4.4가 부족합니다`가 나가면 사용자는 `제약` 칸을 고치면 된다. 항목과 칸이 1:1이라 이 연결이 설명 없이 성립한다.

## 6. 이 형식이 유효한 문제 조건 (출제 기준)

이 형식은 **기존 코드를 수정하는 과제**를 전제한다. 아래를 모두 만족하는 문제에만 적용한다.

1. **기존 코드가 있다** — 빈 스켈레톤에 새로 작성하는 문제가 아니다.
2. **건드리면 안 되는 영역이 있다** — 제약 칸이 채울 내용을 가진다.
3. **완료 판정이 가능하다** — 테스트나 관찰 가능한 기준으로 끝을 정의할 수 있다.
4. **요구사항이 둘 이상이거나 예외 상황이 있다** — 정상 경로 하나뿐이면 요구사항 칸이 목표의 복사가 된다.
5. **명세에 적히지 않은 판단 여지가 있다** — 명세를 그대로 옮기면 풀리는 문제면 형식은 필사 노동이 된다.

문제는 GitLab 문제 저장소 동기화로 공급된다. 위 조건을 만족하는 문제 출제가 이 형식의 선행 조건이다.

## 7. 남용 방지

**칸을 채웠다는 사실은 평가 근거가 아니다.** 아래는 형식을 지켰지만 나쁜 프롬프트다.

- **빈 칸 채우기** — `제약: 기존 기능 유지` 만 매번 반복. 무엇이 기존 기능인지 없으면 정보량 0이다.
- **명세 복붙** — 문제 명세 문장을 칸별로 잘라 붙임. 평가 기준 문서 3장은 이미 제공된 정보를 반복하지 않았다고 감점하지 않는다. 반대로 반복했다고 가점도 없다.
- **과잉지정** — 문제가 요구하지 않은 구현 방식·라이브러리·설계를 지시. 평가 기준 문서 3장의 "문제에 없는 내용을 불필요하게 요구했는지"에 걸린다.
- **길이 부풀리기** — 형식이 길어 보이게 만들려고 문장을 늘림. 길이는 판단 근거가 아니다.

**형식을 생략해도 되는 경우**: 목표·대상·요구사항이 한 문장에 명확히 담기고 수정 범위가 자명한 소형 수정. 이때는 한 줄 프롬프트가 6칸보다 낫다. 형식은 정보를 빠뜨리지 않기 위한 뼈대이지, 제출물의 규격이 아니다.

# pattern 피드백 설계 결정 기록

작성일: 2026-08-04

이 문서는 이 렌즈의 **결정 기록**이다. 제출 한 번이 무엇을 만들어 어떤 모양으로 나가는지는
[제출 피드백 개요](feedback-overview.md)에 있다.

## 목적

제출 피드백에 두 번째 스타일을 나란히 놓는다. [프롬프트 피드백](feedback-design.md)이 프롬프트 문장을
6칸에 재배치해 **무엇을 전달했는지**를 보는 데 비해, 이쪽은 세션에서 벌어진 **작업 방식**에 이름을
붙이고 대응 기법을 가리킨다.

어휘는 aihero.dev의 [AI Coding Dictionary](https://aicodingdictionary.com)에서 가져온다.
코드 전역에서 이 스타일의 이름은 `pattern`이다.

```
TURN 03 PATTERN
  vibe coding — AI가 낸 코드를 읽지 않고 받아들이는 방식
  턴 2에서 AI가 OrderValidator를 새로 만들었어요.
  이 턴 프롬프트에 그 이름이 안 나와요.
  쓸 기법: human review — 이 턴 프롬프트를 쓰기 전에 바뀐 코드를 읽는 것

OVERALL PATTERN
  이번 세션의 이름 — vibe coding
  6턴 중 4턴에서 앞 턴이 바꾼 파일을 프롬프트가 안 짚었어요.
  다음 세션에 가져갈 것: human review
```

## 왜 다른 프레임인가

프롬프트 피드백은 문제 해결 문서다 — 고칠 것만 말한다. 그 프레임에는 잘한 턴을 담을 자리가 없고,
담으면 고칠 턴이 묻힌다.

pattern은 판정이 아니라 명명이다. 이름은 칭찬도 지적도 아니어서 잘한 턴에도 그대로 붙는다.
사전에는 좋은 패턴도 있고(`human review`, `automated check`, `prototyping`),
**이름이 있어야 사용자가 다시 한다.**

| | 프롬프트 피드백 | pattern 피드백 |
|---|---|---|
| 보는 것 | 프롬프트가 전달한 내용 | 사용자가 일한 방식 |
| 지적 대상 | 프롬프트 문장 | 방식. 프롬프트는 그 증거일 뿐이다 |
| 어휘 | 고정 판정 문장 4+5개 | 사전의 일하는 방식 11개, 그중 이름은 4개 |
| 잘한 턴 | 요약 두 문장으로 끝낸다 | 같은 방식으로 이름을 붙인다 |
| 산출물 | 복사해 쓸 프롬프트 | 다음 턴에 해볼 기법 |

## 축 2와 겹치는 지점, 그리고 그은 경계

프롬프트 피드백의 축 2(`AI에 맡기고 확인하지 않으셨어요`)와 `vibe coding`은 **같은 증거**를 읽는다 —
다음 턴 프롬프트에 그 선택이 나오는지다. 사용자 눈에 같은 지적이 두 번으로 읽힐 수 있다.

경계는 시스템 프롬프트로 긋는다. pattern 프롬프트는:

- 프롬프트를 6칸으로 재배치하지 않는다
- 그 라벨 이름을 부르지 않는다
- 결과가 요청을 담았는지 판정하지 않는다
- 복사할 프롬프트를 건네지 않는다

라벨 이름과 고정 판정 문장은 pattern 프롬프트 본문에 **한 글자도 넣지 않는다.** 넣으면 모델이
그쪽 어휘를 되쓰기 때문이다. 그래서 금지 문구도 "그 라벨을 쓰지 마라"가 아니라 "프롬프트를
라벨로 분류하지 마라"로 적는다. `PatternPromptsTest`가 `doesNotContain`으로 이것을 고정한다.

**2026-08-06부로 겹침이 소멸했다.** 코치 축 2는 다음 턴 반응을 더는 읽지 않는다([프롬프트 피드백
설계](feedback-design.md) 참고). 두 렌즈의 질문이 갈렸다 — 축 2는 이 턴에서 누가 방향을 정했나,
pattern은 앞 턴 결과를 이 턴이 짚었나.

## 왜 어휘를 닫았는가

**처음에는 사전 69개를 전부 실었다. 실호출 두 번이 그 결정을 반박했다.**

같은 4턴 세션을 두 번 돌렸더니 두 번 다 어휘가 하나로 무너졌다. 첫 번째는 4턴 중 3턴과 총평이
전부 `primary source`였는데, 그건 원본 자체를 가리키는 **명사**이지 일하는 방식이 아니다. 두 번째는
같은 자리를 `human review`가 차지했고, 없는 사실까지 지어냈다("턴 3의 사용자 말은 배송 시작 주문의
예외만 집어서 물었어요" — 그 턴은 재고 얘기였다).

지시로 막으려던 것이 실패한 이유는 분명하다. 쉰여덟 개가 기계 부품 이름(`token`·`context window`·
`prefix cache`)이라 애초에 이름이 될 수 없는데, **목록에 있다는 것만으로 모델을 끌어당겼다.**
그래서 지시가 아니라 **정보를 뺀다** — 이건 [attempt LLM 제약 설계](../../docs/attempt-llm-constraints.md)가
쓴 "능력이 아니라 재량을 깎는다"와 같은 수다.

`AiCodingDictionary`는 사전의 **Patterns of Work** 절 열한 개만 싣는다. 그중 이름이 될 수 있는 것은
**둘**이고, 프롬프트가 그 둘을 근거와 함께 못 박는다.

| 이름 | 무엇으로 관찰하는가 |
|---|---|
| `vibe coding` | 턴 K-1의 변경 파일이 턴 K 프롬프트에 이름으로 안 나온다 |
| `human review` | 턴 K가 그 파일을 짚거나 고치거나 되돌린다 |

**처음에는 넷이었다.** `human-in-the-loop`과 `design concept`을 같이 열었더니 앞엣것은 둘째 턴이 있는
세션이면 늘 참이라 `vibe coding`을 삼켰고, 뒤엣것은 사용자가 무엇을 그렸는지 추측해야 해서 실행마다
갈렸다. 남긴 둘은 근거가 기계적이다 — 파일 이름은 다음 프롬프트에 있거나 없거나 둘 중 하나다.

나머지 아홉은 목록에 남기되 이름으로는 쓰지 못한다. `AFK`·`automated check`·`automated review`·
`prototyping`은 우리가 기록하지 않는 신호가 있어야 하고, `grilling`은 이 제품의 AI가 되묻지 않으므로
일어날 수 없으며, `DX`·`AX`는 코드베이스를 평가하는 말이지 일하는 방식이 아니다. 설명 문장에서
빌려 쓰는 것은 허용하고, **`쓸 기법` 자리에는 이름 제한이 걸리지 않는다**(아래 절).

둘 중 어느 것도 맞지 않으면 **이름을 붙이지 않는다.** 틀린 이름은 사용자가 검증할 수 없는 라벨이라
이름 없음보다 나쁘다.

입력 토큰도 3,000에서 600 남짓으로 준다.

`AiCodingDictionary`는 영어 원문을 복제하지 않는다 — 그 저장소에 LICENSE가 없다. 용어명은 업계
말이라 그대로 쓰고 뜻풀이만 한 줄로 다시 썼다. 용어 표기는 `원어 — 한국어 풀이`이고 원어는 절대
번역하지 않는다. 사용자가 다음 세션에 가져가는 것이 그 영어 이름이기 때문이다.

출처 한 줄(`PatternPrompts.SOURCE_NOTE`)은 모델에게 맡기지 않고 BE가 총평 뒤에 붙인다. 맡기면
나오다 말다 해서 화면이 흔들린다.

## `쓸 기법`이 조회표였다 — 2026-08-06 실측

"턴마다 `vibe coding`이 뜨고 기법은 `human review`뿐"이라는 관찰에서 시작했다. **이름 쪽은 오류가
아니었다.** 손으로 짠 세션 네 개(15턴)를 실제로 돌려 보니 이름이 갈렸다 — 다음 프롬프트가 바뀐 파일을
짚은 턴은 `human review`, 앞 결과를 한 번도 안 건드린 턴은 `vibe coding`, 마지막 턴과 변경이 없는
턴은 이름 없음. 한 이름으로 무너지지 않는다.

| 세션 | 사용자가 하는 일 |
|---|---|
| MIX (6턴) | 짚음·무시·실행결과로만 확인·되돌리기를 한 세션에 섞음 |
| A (3턴) | 다음 프롬프트가 늘 바뀐 파일 경로를 그대로 씀 |
| B (3턴) | 앞 결과를 한 번도 안 건드림 |
| C (3턴) | 파일 이름은 안 쓰고 매 턴 실행해 본 결과로만 고침 |

**대신 기법 칸이 조회표였다.** 프롬프트가 본문에 답을 적어 둬서(`vibe coding` is answered by
`human review`) 진단이 정해지는 순간 처방이 결정됐다. 같이 나온 것이 둘 더 있었다 — 사용자가 쓴 적
없는 이름을 사용자 발언으로 적은 문장 4개(`minPlayerWidth`는 AI가 지은 변수명인데 "막아 달라고
하셨어요"가 붙었다), 그리고 총평이 `다음 세션에 가져갈 것`으로 **`vibe coding`을 처방한 것** 1건.

세 가지를 고치고 같은 어템프트의 턴 행을 복제해 제출만 다시 불렀다. 입력이 글자 단위로 같은 재측정이다.

| | 고치기 전 | 1차 | 2차(현재) |
|---|---|---|---|
| 턴 기법 | `human review` 3 (전부 같음) | `automated check` 8·`human review` 1 | `automated check` 2·`human review` 4 |
| `vibe coding`이 아닌 턴에 붙은 기법 | 0 | **6** | 0 |
| 총평의 해로운 처방 | 1 | 0 | 0 |
| 사용자 발언·행위 오귀속 | 4 | 2 | **0** |

**1차가 과했다.** `vibe coding`의 답을 둘로 가르면서 "여러 턴에 같은 기법이 맞을 수 있다"고 적었더니
잘한 턴에도 처방이 붙었다. 매 턴 잘한 A 세션이 턴마다 잔소리를 받는다. 2차에서 **이 절은 이름이
`vibe coding`일 때만 쓴다**고 이름으로 못 박아 되돌렸다.

고친 것 셋.

1. **`vibe coding`의 답을 세션이 고르게 한다.** 어느 프롬프트에도 돌려 본 이야기가 없으면
   `automated check`, 돌려 본 이야기는 있는데 코드를 짚은 적이 없으면 `human review`. 2차 측정에서
   B 세션이 전자로, C·MIX가 후자로 갈렸다 — 노린 그대로다. 이름 칸의 제한(둘)은 그대로 두고
   **기법 칸에만 사전 열한 개를 연다.**
2. **사용자를 주어로 쓸 때는 사용자 말만 쓴다.** 경로·클래스·변수는 `<user_prompt>`에 그 글자가
   있을 때만 사용자의 말이다. 사용자가 코드를 고쳤다고 쓰는 것도 같이 막는다 — 사용자는 부탁하고
   AI가 고친다. 예문이 규칙보다 세게 가르치므로 둘 다 예문으로 싣는다.
3. **처방 자리에 올 수 있는 용어를 목록으로 못 박는다.** `vibe coding`은 다음 세션에 가져갈 것이
   될 수 없다. "세션 이름과 다른 용어" 하나로는 해로운 방식이 그 자리에 오는 것을 못 막았다.

**부수 효과 하나.** 2차에서 C 세션의 이름이 `human review` → `vibe coding`으로 옮겨 갔다. C 사용자는
코드를 한 줄도 안 읽고 실행 결과만 말한다 — 사전의 `human review`는 diff를 읽는 것이므로 이쪽이 맞다.
기법 조건이 "돌려 봤는가 / 읽었는가"를 갈라 적으면서 이름 판정도 같이 정렬됐다.

### 흔들리는 자리는 둘뿐이다

같은 입력을 세 번 더 돌렸다(15턴 × 3회).

| | 결과 |
|---|---|
| 3회 모두 같은 판정 | 15턴 중 13턴 |
| 흔들린 턴 | 2턴 |
| `vibe coding`이 아닌 턴에 붙은 기법 | 3회 모두 0 |
| 사용자 오귀속 | 3회 모두 0 |

흔들린 둘은 정확히 경계에 있다.

- **다음 프롬프트가 실행 결과만 말하는 턴** — `vibe coding` 2회, `human review` 1회. 돌려 본 것을
  읽은 것으로 셀지가 갈린다.
- **다음 프롬프트가 앞 턴의 결정을 되돌리는 턴** — `human review` 2회, `vibe coding` 1회. 규칙은
  되돌리기를 읽은 증거로 치므로 `human review`가 맞고, 어긋난 1회가 흔들림이다.

**둘 다 "읽었다"와 "돌려 봤다"의 경계다.** 이름 어휘를 둘로 좁힌 결정이 이 경계를 한 이름 안에
접어 둔 대가이고, 지금 남은 유일한 불안정이다.

### 하네스가 pattern 렌즈를 채점한다

`LiveFeedbackHarnessTest`는 판정 정확도를 프롬프트 렌즈에만 매겼다 — pattern 행의 `judgements`가
전부 `null`이었고, **이 렌즈의 이름은 한 번도 채점된 적이 없었다.** 네 지표를 더한다.

| 지표 | 무엇을 잡는가 |
|---|---|
| 이름 정확도 | `### 이 턴의 이름`의 용어가 기대와 같은가 |
| 기법 정확도 | `### 쓸 기법`의 용어가 기대와 같은가. 절이 없어야 하는 자리도 함께 본다 |
| `vibe coding`이 아닌 턴에 붙은 기법 | 잘한 턴에 처방이 붙으면 잔소리가 된다 |
| 사용자 오귀속 | 사용자가 쓴 적 없는 이름이 사용자 발언·행위로 적혔는가 |

마지막 지표는 부정문을 뺀다. `사용자가 AI가 고친 index.html을 턴 2에서 안 부르셨어요`에서 그 경로는
`<changed_file>`에서 온 정당한 근거이고, 문장이 말하는 것은 사용자가 그것을 말하지 **않았다**는
사실이다. 이걸 안 빼면 정답이 위반으로 잡힌다.

**픽스처도 둘 늘렸다.** 기존 다섯은 전부 `직전 결과 … 확인했어요`로 시작해 `vibe coding` 축을 거의
재지 못했다. S6 안 짚음(→ `automated check`)과 S7 실행으로만 확인(→ `human review`)이 그 축과
기법 갈림을 맡는다.

## 이름은 코드가 정한다 — 2026-08-06

위의 실측은 전부 `gpt-5.4-mini`에서 잰 것이었다. `.env`의 `OPENAI_FEEDBACK_MODEL`이 코드 기본값을
덮고 있어 **두 피드백 렌즈만 다른 모델로 돌고 있었다**(`CODE`는 luna, `FEEDBACK`·`PATTERN_FEEDBACK`은
mini). 그 줄을 luna로 바꾸자 같은 프롬프트가 정반대로 틀렸다.

**이 절 아래로는 전부 luna에서 잰 값이다.** 세 경로의 현재 기본값은 `gpt-5.6-luna`이고, 이 문서가
`gpt-5.4-mini`를 부르는 자리는 여기까지의 이력뿐이다.

| | S1·A 잘한 세션 | S6·B 한 번도 안 짚음 | S7·C 실행으로만 확인 |
|---|---|---|---|
| 원래 규칙 · mini | **vibe coding** ✗ | vibe coding ✓ | vibe coding |
| 원래 규칙 · luna | 이름 없음 | **이름 없음** ✗ | vibe coding |
| 문구를 넓힘 · luna | human review | **human review** ✗ | human review |

**판본마다 다른 세션을 틀렸다.** 프롬프트는 줄곧 이렇게 적어 두고 있었다.

> the evidence for them is mechanical: a file name is either in the next prompt or it is not.

**그런데 그 기계적인 일을 모델에게 시키고 있었다.** 그래서 문구와 모델이 바뀔 때마다 라벨이 통째로
뒤집혔다. 이건 문구를 더 고쳐서 될 일이 아니다 —
[에이전트 패턴 조사](../../docs/agent-patterns.md)가 문헌으로 정리한 결론이 정확히 이 자리를 가리킨다:
**모델에게 판단시키지 말고 코드에게 판단시킨다.**

`PatternPrompts`가 턴 K-1의 변경 파일이 턴 K 프롬프트에 나오는지를 경로·파일명·확장자 뗀 이름 셋으로
보고, 결과를 `<prompt_names_previous_changed_file>` 태그로 **사용자 데이터보다 앞에** 싣는다.
`FeedbackPrompts.appendTag`는 이스케이프를 하지 않으므로 사용자 프롬프트 안의 여는 꺾쇠를 죽이고,
프롬프트가 "첫 번째만 센다"고 못 박는다.

### 이름을 자유 텍스트에 두면 모델이 빼먹는다

태그를 주자 **틀린 이름은 사라졌지만 기권이 남았다** — 모델이 이름을 달 때는 계산값과 100% 일치했고,
대신 호출의 40%가 세션 전체에서 이름을 통째로 빼먹었다. 경쟁하던 지시 둘을 걷어내고
(`둘 중 어느 것도 안 맞으면 이름을 붙이지 마라`, `이름 붙일 것이 없으면 한 문장으로 끝내라`) 근거
태그 목록에 이 태그를 더해도 62.5% → 59.4%로 노이즈 안이었다.

**그래서 이름을 스키마로 받는다.** `turnFeedbacks[]`가 `name`(enum)과 `gloss`를 갖고, 제목 줄은
BE가 조립한다(`PatternPrompts.renderTurn`). 모델의 `feedback`은 근거 문장부터 시작한다. 이 저장소가
턴 개수에서 이미 배운 것과 같은 수다 — **지시로 안 되던 것이 스키마로 됐다.**

| luna, 7세션 × 2회 | 태그만 | 경쟁 지시 제거 | 스키마 |
|---|---|---|---|
| 이름 정확도 | 50.0% | 62.5% | **100% (32/32)** |
| 이름 없음 | 30 | 26 | **14** (마지막 턴 정확히 그만큼) |
| 기법 정확도 | 40.0% | 80.0% | 80.0% |
| `vibe coding` 아닌 턴에 붙은 기법 | 0 | 0 | 0 |
| 사용자 오귀속 | 0 | 0 | 0 |

계약 실패 1/28은 프롬프트 렌즈의 잘림이고 이 변경과 무관하다.

**대가는 엄격해진 것이다.** 파일 이름 없이 결과를 말로만 확인한 턴은 `vibe coding`이 된다 —
사전의 `vibe coding`이 "diff를 안 열고 동작만 본다"이므로 뜻은 맞지만, `직전 결과 … 확인했어요`로
이어 가는 성실한 세션도 그렇게 불린다. **그 차이는 이름이 아니라 기법이 맡는다** — 돌려 본 이야기가
어디에도 없으면 `automated check`, 돌려는 봤는데 코드를 안 짚었으면 `human review`.

## 피드백이 뒤만 본다 — 2026-08-06 재귀속

**문제는 턴 1의 절이 턴 2를 사실로 주장한 것이다.** 이름을 계산값에서 읽게 하면서 판정이 안정됐지만,
그 계산이 보는 것은 다음 턴 프롬프트였다. 그래서 턴 1 피드백이 사용자가 아직 열지 않은 턴 2에서
무엇을 했는지부터 말했다. 읽는 순서가 깨지면 근거를 검증할 수 없다.

**결정: 판정 내용은 그대로 두고 붙이는 턴만 한 칸 뒤로 옮긴다.** 대조 방향도 스키마도 FE 구조도
그대로다 — 같은 계산의 결과를 턴 K-1이 아니라 턴 K에 싣는다.

규칙 넷.

- **첫 턴은 이름이 없다.** 짚을 앞선 결과가 없다.
- **마지막 턴도 이름을 받는다.** 증거가 앞 턴이라 마지막 턴에만 없던 자리가 사라졌다.
- **앞 턴이 아무 파일도 안 바꿨으면 그 턴도 이름이 없다.** 짚을 것이 없는 턴을 `named=false`로
  실으면 `vibe coding`으로 오판된다. 줄이 하나도 안 남으면 태그 자체를 싣지 않는다.
- **근거는 둘뿐이다** — 턴 K-1의 변경 파일과 턴 K의 프롬프트(그리고 턴 K 자신의 툴콜). 뒤 턴이
  무엇을 했는지는 이 절의 근거가 아니다.

`쓸 기법`도 같이 회고형으로 바꿨다. "다음 턴에 이렇게 하세요"는 사용자가 아직 안 읽은 턴을
가리키므로, "이 턴 프롬프트를 쓰기 전에 이렇게 했다면"으로 적는다.

### 실측 — 재귀속 전후

같은 픽스처 7세션을 같은 모델로 돌렸다.

| luna, 7세션 × 2회 | 재귀속 전 | 재귀속 후 |
|---|---|---|
| 이름 정확도 | 100% (32/32) | **100% (32/32)** |
| 이름 없음 | 14 — 전부 마지막 턴 | **14 — 14/14 호출에서 전부 첫 턴** |
| 기법 정확도 | 80% (깨진 파서로 잰 값, 아래) | **100% (10/10)** |
| `vibe coding` 아닌 턴에 붙은 기법 | 0 | **0** |
| 사용자 오귀속 | 0 | **0** |
| 계약 성공 | 27/28 | **28/28** |
| 축 2 마지막 턴 판정 분포 | 해당 없음(전용 문장 고정) | `AI에 맡기셨어요` 10 · `방향을 정하셨어요` 3 · 없음 1 |

**이름 이동은 한 호출도 안 흔들렸다.** 세 번 돌리는 동안 매번 32/32였고, 빈 이름의 위치도 매번
첫 턴이었다. 마지막 턴은 이제 전부 이름을 받는다.

**축 2의 마지막 턴이 처음으로 판정을 받았다.** 14호출 중 13이다. 남은 하나는 축 2가 실패한 것이
아니라 절 자체가 없는 턴이다 — 판정 1도 비어 있다. "지적할 것이 없으면 요약 두 문장으로 끝낸다"는
기존 경로이고 이 변경과 무관하다.

`턴스코프 불일치`는 0에서 16으로 올랐다. 인용이 앞 턴의 `<changed_file>`에서 오는 것이 이제
정답이므로 이 숫자는 위반이 아니라 진단값이다. 원문 일치율은 여전히 100%다.

### 기법 지표가 마크업을 재고 있었다

**두 번을 헛짚었다.** 재귀속 직후 기법 정확도가 80% → 60%로 떨어져 보였고, 원인을 "회고형으로
바꾸면서 절이 사라졌다"로 읽고 프롬프트에 `모든 vibe coding 턴은 이 절을 갖는다`를 못 박았다.
그러자 40%로 더 떨어졌고 용어가 `human review` 하나로 무너졌다 — 이 문서가 08-04에 이미 적어 둔
조회표 실패 모드다. 되돌렸다.

**세 번째에 하네스가 생성 텍스트를 함께 남기게 하고 나서야 원인이 보였다.** 절은 하나도 안
빠져 있었다 — `vibe coding` 턴 **서른 개 전부**에 `### 쓸 기법`이 있었다. 못 읽은 것은 파서다.

```
rep1  automated check — 이 턴 프롬프트를 쓰기 전에…      ← 읽힘
rep2  `automated check` — 이 턴 프롬프트를 보내기 전에…  ← null로 잡힘
```

`termAfter`가 `line.startsWith(term)`으로 보는데 모델이 용어를 백틱으로 감싸면 걸린다. 서른 턴 중
열셋이 그렇게 빠졌고 그중 열둘이 백틱이었다. 여는 백틱을 벗기고 다시 채점하니 **10/10**이다.

**표에 적힌 80%도 같은 파서로 잰 값이다.** 그래서 재귀속 전후를 이 칸으로 비교할 수 없다 — 80%와
100%의 차이는 모델이 아니라 그날 모델이 백틱을 얼마나 썼는지다.

배운 것은 지표 쪽이다. **지표가 떨어졌을 때 생성물을 안 보고 프롬프트를 고치면, 측정 버그를
모델 탓으로 돌리고 멀쩡한 프롬프트를 망친다.** 그래서 `CallRecord.turnTexts`를 남긴다.

남은 흠 하나: 서른 턴 중 하나가 절은 썼는데 용어로 시작하지 않았다(`이 턴 프롬프트를 보내기 전에…`).
프롬프트가 이미 용어를 먼저 쓰라고 적고 있고 1/30이라 손대지 않았다.

## 툴콜 트레이스

pattern 프롬프트만 턴별 툴콜을 싣는다.

```
<tool_calls turn="2">
list_files
read_file src/main/java/OrderService.java
edit_file src/main/java/OrderService.java
</tool_calls>
```

트레이스는 결과에 남지 않은 탐색 순서다. AI가 무엇을 읽고 무엇을 고쳤는지는 여기에만 있고,
작업 방식을 보는 렌즈에는 그게 근거가 된다. `AttemptView.TurnView.toolCalls()`가 이미 채워져
있어 새 배관은 없다.

프롬프트 피드백에는 넣지 않는다. 트레이스를 범위 밖에 둔 것은 **결과로 판정한다**는 그쪽 원칙이지
새 렌즈의 원칙이 아니다.

## 왜 둘 다 필수인가

한쪽만 나온 화면은 만들지 않는다. 두 스타일은 같은 세션의 다른 면이라, 하나가 빠지면 사용자는
없는 쪽이 원래 없는 것인지 실패한 것인지 알 수 없다.

`Attempt.submit`이 두 목록의 개수를 각각 턴 수와 대조하고, 어느 한쪽이라도 어긋나면 저장하지
않는다(`FeedbackTurnCountMismatchException` 재사용).

**대가는 제출 실패율이 대략 두 배가 되는 것이다.** 각 생성기 안의 1회 재호출이 그 절반을 되돌린다.

## 두 호출을 합치는 곳

포트(`FeedbackGenerator`)를 구현하는 것은 `FeedbackGenerators` 하나뿐이다. 구현이 둘이 되면
운영 컨텍스트가 `NoUniqueBeanDefinitionException`으로 부팅에 실패하고, `@Primary`를 붙이면
테스트의 가짜 생성기와 충돌한다. `OpenAiFeedbackGenerator`는 포트를 구현하지 않는 렌즈 하나짜리
어댑터이고, 렌즈마다 다른 것은 시스템 프롬프트·유저 프롬프트 조립·호출 옵션·로그 태그 넷뿐이라
클래스를 복제하지 않고 그 넷만 생성자로 받는다.

두 호출은 `AiCallExecutor.submit`으로 동시에 띄운다. 못 박아 둔 것 셋:

1. **바깥에 타임아웃을 두지 않는다.** 상한은 각 생성기 안의 `AiCallExecutor.call(..., 5분)`이
   이미 갖는다. 바깥에서 또 재면 자기 예산 안에서 정상 진행 중인 브랜치를 자르고, 그 브랜치의
   사용량 tracker가 들고 있던 토큰이 통째로 사라진다.
2. **실패해도 반대쪽을 취소하지 않는다.** `future.cancel(true)`는 바깥 작업 스레드만 인터럽트하고,
   그 스레드가 블로킹 중인 안쪽 `call`은 자기 future를 취소하지 않는다 — AI 호출은 죽지 않고
   토큰만 과금된 채 결과를 아무도 읽지 않는다. 취소는 두 번 거짓말한다.
3. **executor는 태스크마다 스레드를 새로 만들어야 한다.** `submit`이 띄운 작업이 안에서 다시
   `call`을 부르는 2단 구조라, 고정 크기 풀로 바꾸면 바깥 둘이 풀을 채우고 안쪽 둘이 큐에서
   굶어 데드락이 된다.

## 실패 경로에서 purpose를 안 나누는 이유

성공 경로는 `attempt_llm_call.purpose`를 `FEEDBACK`과 `PATTERN_FEEDBACK`으로 나눠 저장한다.
purpose가 갈리므로 두 목록이 각자 1부터 매긴 seq를 그대로 써도 충돌하지 않는다.

실패 경로는 나누지 않는다 — 두 브랜치의 사용량을 합쳐 seq를 1..N으로 다시 매기고 `FEEDBACK`
하나로 남긴다.

| 선택지 | 평가 |
|---|---|
| **합쳐서 FEEDBACK 하나로 (채택)** | 실패는 제출 한 건의 사건이다. 어느 렌즈가 무너졌는지는 이미 로그에 있고, 실패 행에서 다시 물을 일이 없다 |
| 브랜치별 purpose + 각자 FAILED 마커 | 한 번의 실패에 마커가 둘 생긴다. 실패 건수를 세는 쿼리가 전부 두 배로 읽힌다 |
| 실패한 쪽 purpose만 | 성공한 쪽이 쓴 토큰이 실패 기록에서 사라진다 |

던지는 예외도 하나다. 어느 한쪽이 `FeedbackTimeoutException`이면 타임아웃(504)이 이긴다 —
사용자가 실제로 겪은 것은 5분을 기다린 일이다. 아니면 실패한 쪽의 `reason`을 보존한
`FeedbackGenerationException`이다. `FeedbackResponseException`(재시도 대상 표식)으로는 던지지
않는다 — 재호출은 각 생성기 안에서 이미 끝났다. 새 예외 타입은 만들지 않아
`GlobalExceptionHandler`의 502/504 매핑을 그대로 타고, API 에러 계약이 바뀌지 않는다.

## 응답 봉투

기존 봉투에 필드만 더한다. FE는 모르는 키를 무시하므로 FE 변경 없이 배포된다.

```json
{
  "turns": [{ "turn": 1, "feedbackMd": "...", "patternMd": "..." }],
  "overallMd": "...",
  "patternOverallMd": "..."
}
```

`turns`를 채울지는 프롬프트 피드백만 보고 정한다. 둘 다 필수라 pattern만 있는 상태가 생기지
않기 때문이다. **구버전 공존**: pattern 도입 전에 제출된 어템프트는 두 pattern 필드가 `null`로
나간다. 기존 데이터를 마이그레이션하지 않는다.

## 문체

두 스타일이 `FeedbackWritingStyle.section(...)`을 공유한다. 사용자가 한 화면에서 둘을 나란히 읽으므로
한쪽만 고치면 같은 화면 안에서 목소리가 갈린다. 규칙 본문은 [프롬프트 피드백 문서](feedback-design.md)에
있다.

## 호출 옵션

모델은 프롬프트 피드백과 같고(기본값 `gpt-5.6-luna`, 슬롯별 `OPENAI_FEEDBACK_MODEL`로 덮인다)
effort는 한 단계 위인 `medium`이다.

| | base | 턴당 | 상한 |
|---|---|---|---|
| 프롬프트 피드백 | 4,096 | 2,048 | 32,768 |
| pattern 피드백 | 8,192 | 2,048 | 32,768 |

출력 문장 자체는 프롬프트 렌즈의 절반 이하인데도 예산이 더 크다. reasoning이 같은 완성 토큰 예산에서
나가고 `medium`은 그것을 많이 쓰기 때문이다 — 6턴 호출이 reasoning에만 4,979~13,879 토큰을 쓴 실측이
`OpenAiChatOptionsFactory`에 남아 있다. 잘림은 재시도 대상이 아니고 pattern은 프롬프트 렌즈와 함께
필수라, 예산이 모자라면 제출이 통째로 실패한다.

두 호출 모두 워크로드 고정 프롬프트 캐시 키를 싣는다(`feedback` / `pattern-feedback`). 시스템
프롬프트가 전 사용자·전 제출에서 같아 프리픽스가 통째로 캐시되고, 사용자 데이터는 프리픽스 뒤에
와서 섞이지 않는다. 키를 갈라야 하는 이유는 두 시스템 프롬프트가 다르기 때문이다 — 같은 키를
주면 프리픽스가 어긋나 캐시가 빗나간다.

## 범위 제외

| 항목 | 이유 |
|---|---|
| 스타일 목록으로 일반화 | 쓰이지 않을 축을 도메인에 미리 넣지 않는다. 컬럼 하나씩만 더한다 |

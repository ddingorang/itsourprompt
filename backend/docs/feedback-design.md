# 턴별 프롬프트 피드백 설계 결정 기록

작성일: 2026-07-30
개정: 2026-08-03 (소제목·판정 문장·문체)

## 목적

- 제출 시 생성하는 피드백을 어템프트 전체 한 덩어리가 아니라 **턴별**로 나눈다.
- 각 턴의 사용자 프롬프트를 [결과 형식](prompt-format.md)의 6칸으로
  **프롬프트 정리하기 → 결과와 비교하기 → 다음 프롬프트 쓰기** 한다.
- 두 축을 판정한다. 축 1은 요구가 반영됐는지, 축 2는 방향 결정을 사용자가 했는지 AI에 위임했는지다.
  축 이름은 내부 어휘다 — 사용자에게는 축 이름 없이 판정 문장만 나간다.

평가 대상은 프롬프트뿐이다. 코드 품질은 판정하지 않고 정답 여부는 사용자에게 내보내지 않는다 —
채점 결과는 판정의 근거로만 읽는다([경계가 옮겨간 자리](#경계가-옮겨간-자리-2026-08-05) 참고).

같은 세션을 다른 렌즈로 보는 두 번째 스타일이 나란히 실린다 —
[pattern 피드백](pattern-feedback-design.md)은 작업 방식에 이름을 붙인다. 두 스타일은 문체
상수(`FeedbackWritingStyle`)를 공유하고 어휘와 절 제목은 겹치지 않게 갈라 둔다.

## 응답 봉투

턴 분할만 스키마로 고정하고 내용은 markdown으로 둔다.

```json
{
  "turns": [{ "turn": 1, "feedbackMd": "..." }],
  "overallMd": "..."
}
```

| 선택지 | 평가 |
|---|---|
| **최소 봉투(턴 번호 + markdown) (채택)** | 렌더 단위가 고정되고 내용 형식은 프롬프트만 고쳐 바꿀 수 있다 |
| 축·판정·근거까지 필드로 고정 | 어휘를 바꿀 때마다 스키마·DTO·FE가 함께 움직인다 |
| 전체를 markdown 한 덩어리로 | 턴별 접기·턴 이동 같은 FE 표현이 불가능하다 |

확장은 additive로만 한다 — 필드를 추가하되 기존 필드의 의미·형태는 바꾸지 않고, FE는 모르는 키를 무시한다.

**구버전 공존**: 이 변경 전에 제출된 어템프트는 턴 피드백이 `null`이다. 그런 어템프트는 `turns`가
빈 배열로 나가고 FE는 `overallMd`만 렌더한다. 기존 데이터를 마이그레이션하지 않는다.

## 문서 유형

턴 피드백과 총평은 같은 글이 아니다. 유형을 갈라야 각자의 분량과 어조가 정해진다.

| | 유형 | 독자가 이걸 읽고 하는 일 |
|---|---|---|
| 턴 피드백 | 문제 해결 문서 | 다음 턴에 쓸 프롬프트를 고친다 |
| 총평 | 깊은 이해 문서 | 다음 세션에 가져갈 습관을 안다 |

턴 피드백이 문제 해결 문서라는 것은 3단 구조에 그대로 대응한다 — 현상(요약)·원인(결과와
비교하기)·해결(다음 프롬프트 쓰기). 보내기 전에 셋이 다 있는지 확인한다.

총평은 고칠 목록이 아니다. 왜 그 패턴이 세션 내내 유지됐는지를 설명한다. 그래서 총평에는
프롬프트 예시를 두지 않는다.

## 턴별 피드백 3단 구조

각 턴은 요약 두 문장으로 연다. 첫 문장은 이 턴에서 무엇이 어긋났고 원인이 무엇인지, 둘째 문장은
고치면 무엇이 달라지는지를 말한다. 소제목 뒤에 요약을 두지 않는 이유는 독자가 접힌 카드에서
첫 두 줄만 보고도 이 턴을 열어볼지 정할 수 있어야 하기 때문이다.

| 단계 | 소제목 | 하는 일 |
|---|---|---|
| ① | `### 프롬프트 정리하기` | 사용자 프롬프트를 6칸에 재배치한다. 사용자 표현을 인용하고, 정보가 없는 칸은 `(없음)`으로 표시한다 |
| ② | `### 결과와 비교하기` | 빈 칸·모호한 칸이 실제 변경 파일에 남긴 흔적을 연결하고 두 축을 판정한다 |
| ③ | `### 다음 프롬프트 쓰기` | 개선된 프롬프트 예시를 준다. 턴 1은 6칸 전체, 턴 2+는 `직전 결과` + 바뀐 칸만 |

소제목을 동사형으로 통일한 이유: `변환`·`대조`·`처방`은 우리가 하는 일의 이름이지 독자가 얻는
것의 이름이 아니다. 소제목만 훑는 독자가 절을 열지 말지 정할 수 있어야 한다.

정리 단계가 먼저인 이유: 사용자는 결과 형식을 모르는 상태로 프롬프트를 쓴다. 자기 문장이 6칸에
어떻게 배치되는지 먼저 보여야 어느 칸이 비어 있었다는 지적이 성립한다. 피드백 자체가 형식의
노출 채널이다 — 형식 가이드를 별도로 읽히지 않는다.

**지적할 게 없는 턴은 요약 두 문장으로 끝낸다.** 세 절을 형식대로 채우면 잘한 턴과 못한 턴의
피드백 분량이 같아져, 어느 턴을 고쳐야 하는지가 묻힌다.

## 축 1 — 요구 반영

**판정 경계**: 프롬프트 문장, 그 턴의 변경 파일, 그리고 그 턴의 채점 결과를 본다. 코드 품질 평가와
해답 코드 제공은 여전히 금지다.

| 사용자에게 나가는 문장 | 의미 | 이어지는 코칭 |
|---|---|---|
| `요청한 대로 바뀌었어요` | 요구한 변경이 결과에 있고 **동작한다** | — |
| `일부만 바뀌었어요` | 일부만 반영됐다 — 변경은 있는데 요구한 동작을 못 하는 턴도 여기다 | 빠진 부분이 어느 칸의 공백에서 왔는지 |
| `요청이 프롬프트에 없었어요` | 프롬프트가 전달하지 못했다 | 어느 칸이 부족했는지 연결 |
| `요청하셨지만 AI가 하지 않았어요` | 요구가 변경 파일에 통째로 없다 | 다음 턴 재지시 방법 |

프롬프트 원인과 실행 실패를 나눈 이유: 사용자가 고칠 수 있는 것만 프롬프트 코칭으로 돌린다.
실행 실패를 프롬프트 탓으로 돌리면 고칠 수 없는 지적이 된다.

### 경계가 옮겨간 자리 (2026-08-05)

턴별 채점 결과가 판정 입력에 들어오면서 `요청한 대로 바뀌었어요`의 뜻이 "결과에 있다"에서
"결과에 있고 동작한다"로 바뀌었다. 문장을 하나도 늘리지 않았는데 **"정답 여부는 판정하지 않는다"는
경계가 이동한 것**이고, 이 설계의 유일한 합의 사항이다.

**요구한 동작의 테스트가 실패한 턴은 `일부만 바뀌었어요`다.** `요청하셨지만 AI가 하지 않았어요`가
아니다 — 그 문장은 요구가 변경 파일에 **통째로** 없을 때의 자리로 이미 정의돼 있고, 변경이 파일에
있는데 그 문장을 쓰는 것은 모순 목록이 금지한 짝이다. 대신 `일부만 바뀌었어요`가 넓어진다.

그러면 실행 실패를 프롬프트 탓으로 돌리게 되지 않나 — 코칭이 "어느 칸의 공백"을 짚기 때문이다.
그래서 채점 결과가 근거일 때는 **공백을 만들어 내지 말고 실패한 테스트 이름으로 어느 동작이 빠졌는지
짚는다.** 짚을 칸이 없으면 칸 이야기를 하지 않는다.

| 채점 결과 | 판정 |
|---|---|
| 실행 없음 (`<test_result>` 없음) | 파일만 보고 판정. 통과 0건이 아니다 |
| `RUNNER_ERROR` (`passed=unknown`) | 파일만 보고 판정. **언급 자체를 금지** — 누구에 대한 정보도 아니다 |
| 델타 음수 | 앞 턴이 통과시키던 것을 이 턴이 깼다는 뜻이니 근거에 적는다 |

통과 개수·비율·정답 여부는 사용자에게 내보내지 않는다. 실패한 테스트 **이름**은 허용한다 — 그것은
채점이 아니라 어느 동작이 아직 빠졌는지를 말하는 근거다.

## 축 2 — 방향 소유

명세에 답이 없는 결정을 사용자가 지정했는지, AI에 맡겼는지를 본다. 3단 관찰로 판정한다.

1. **결정 지점 식별** — 변경 파일에서 명세가 정하지 않은 선택이 이뤄진 지점을 찾는다.
2. **프롬프트 대조** — 그 지점에 대한 방향 표현이 프롬프트에 있었는지 본다.
3. **다음 턴 반응** — 사용자가 그 선택을 확인했는지 다음 턴 프롬프트에서 읽는다.

| 사용자에게 나가는 문장 | 조건 |
|---|---|
| `방향을 정하셨어요` | 프롬프트가 방향을 정했다 |
| `AI에 맡기고 다음 턴에서 확인하셨어요` | 프롬프트엔 없었지만 다음 턴에서 그 선택을 확인한 흔적이 있다 |
| `AI에 맡기고 확인하지 않으셨어요` | 프롬프트에도 없고 다음 턴에서도 언급이 없다 |
| `이 턴에는 판단할 만한 결정 지점이 없었어요` | 명세가 열어둔 결정이 이 턴에 없다 |
| `이 턴이 마지막이라, AI가 정한 것을 확인하셨는지는 알 수 없어요` | **마지막 턴 고정값** |

마지막 턴에 전용 문장을 둔 이유: 검토 흔적의 증거가 다음 턴 프롬프트인데, 마지막 턴에는 다음 턴이
없다. 없는 증거로 위임을 단정하지 않는다. 근거 없음과 마지막 턴은 독자에게 다른 사실이라 옛 `확인 불가`
하나를 둘로 나눴다 — `판단할 근거가 없어요`만 던지면 무엇을 판단 못 하는지가 빠진다.

의도는 단정하지 않는다. 수단은 조건절이 아니라 시제다 — **관찰은 지난 사실로, 처방은 다음 턴에
쓸 것으로** 적는다. `~했어야 해요`는 쓰지 않는다. 이미 지나간 턴에 의무를 지우면 고칠 수 없는
지적이 되고, 사용자가 그렇게 하려 했는지를 단정하게 된다.

## 판정 어휘 통제

두 축의 판정은 위 표의 문장을 **변형 없이 그대로** 내보낸다. 축 이름(`축 1`·`축 2`·`요구 반영`·
`방향 소유`)과 옛 판정값(`반영`·`부분 반영`·`미반영`·`지정`·`위임`·`확인 불가`)은 사용자에게
노출하지 않는다 — 상태 이름은 우리 내부 어휘이고, 사용자가 읽을 것은 자기가 무엇을 했는가다.

6칸 라벨(목표/작업 대상/요구사항/제약/완료 조건/검증)과 후속 턴의 `직전 결과`도 변형을 금지한다.
어휘가 흔들리면 사용자가 피드백과 [형식 문서](prompt-format.md)를 연결할 수 없고, 같은 상태에
다른 이름이 붙는다.

## 문체

문체 규칙은 `FeedbackWritingStyle.SECTION`에 있고 두 피드백 스타일이 같이 끼워 쓴다. 사용자가
한 화면에서 둘을 나란히 읽으므로 한쪽만 고치면 목소리가 갈린다. 배포된 백엔드가 런타임에
참조해야 하므로 이 저장소의 다른 프롬프트와 같이 Java text block에 담는다 — 별도 리소스 파일을
두지 않는다.

| 항목 | 규칙 |
|---|---|
| 어미 | 해요체. 서술 `~해요`, 권유 `~하세요` |
| 주어 | 사용자가 한 일은 `~하셨어요`, AI가 한 일은 `AI가 ~했어요`. 프롬프트·파일·시스템을 주어로 쓰지 않고 피동형도 쓰지 않는다 |
| 단어 | 파생 명사 대신 동사. 연결어(`다음으로`·`결론적으로`류)와 모호어(`가능성이 있다`류) 금지 |
| 구체성 | 파일·메서드·값을 이름으로 부르고, 빠진 것도 이름으로 말한다 |
| 시제 | 관찰은 지난 사실, 처방은 다음 턴에 쓸 것 |
| 분량 | 절당 4문장 상한 |

**경계**: 해요체는 사용자에게 보이는 피드백 문장에만 적용한다. [형식 문서](prompt-format.md)의
`검증` 칸 기본 문구, 예외 메시지, 로그는 그대로 둔다 — 그 문장들의 독자는 사용자가 아니다.

이 절은 매 제출마다 입력 토큰으로 나가지만 프리픽스 캐시에 얹혀 있다 —
`OpenAiChatOptionsFactory.forFeedback()`이 워크로드 고정 키 `feedback`을 싣고, 사용자 데이터는
프리픽스 뒤에 와서 섞이지 않는다. 그래도 규칙과 핵심 Don't/Do 예문만 남기고 45~55줄로 유지한다 —
캐시 미스인 첫 호출과 캐시 토큰의 단가는 그대로 남기 때문이다.

## 남용 방지

프롬프트 코칭이 "칸을 채우라"는 잔소리로 퇴화하는 것을 막는다.

- **칸 존재가 아니라 정보 존재로 판정한다** — 산문 한 줄에 수정 범위가 담겨 있으면 제약은 충족이다.
- **정보량 0인 칸은 인정하지 않는다** — `제약: 기존 기능 유지`류.
- **소형 수정의 한 줄 프롬프트는 정상으로 인정한다** — 빈 칸을 나열해 지적하지 않는다.
- **명세에 없는 구현 방식·라이브러리 지시는 과잉지정으로 지적한다**.

## overall

세션 전체 패턴만 다룬다: 위임 반복, `직전 결과` 습관, 턴에 따른 프롬프트 진화. 여기에 잘한 점과
최우선 개선 1~2개를 붙인다. 개선된 프롬프트 예시는 턴별 `다음 프롬프트 쓰기`에만 두고 overall에는
두지 않는다.

## 생성 시점: 제출 시 일괄 (유지)

| 선택지 | 평가 |
|---|---|
| **제출 시 전체 턴을 한 번에 (채택)** | 축 2가 "다음 턴 반응"을 증거로 쓰므로 턴 N 판정에 턴 N+1이 필요하다 |
| 턴마다 즉시 생성 | 턴 N 시점에 다음 턴이 없어 축 2가 전부 마지막 턴 고정값이 된다 |

턴마다 생성하면 피드백이 다음 턴 프롬프트에 섞여 들어가 평가 대상이 오염되는 문제도 있다.

## 채택 기술

- **json_schema 구조화 출력** — 봉투를 파싱 실패 없이 받는다. Spring AI가 `strict=true`를 고정하므로
  모든 object는 `additionalProperties: false`이고 모든 속성이 `required`에 있어야 한다.
- **완성 토큰을 턴 수에 비례** — 턴별 3단 구조라 출력 길이가 턴 수에 따라 늘어난다. 고정값이면
  긴 세션에서 잘린다.
- **구분자 격리** — 신뢰할 수 없는 데이터(명세·스켈레톤·사용자 프롬프트·AI 요약·변경 파일)를 각각
  태그로 감싸 지시와 구분한다. 사용자 프롬프트가 시스템 지시를 덮어쓰는 것을 막는다.
- **턴 수 검증** — 응답의 턴 피드백 개수가 어템프트 턴 수와 다르면 실패로 처리한다. 턴과 피드백의
  1:1 대응은 봉투의 계약이다.
- **근거 인용 대조** — 턴마다 `quotes`를 필수로 받아 그 문장이 입력에 정말 있었는지 코드가 대조한다.
  없으면 응답 계약 위반으로 한 번 다시 부른다. 봉투의 둘째 계약이며, 저장되는 것은 바뀌지 않는다 —
  인용은 대조를 마치면 버린다. 짚을 것이 없는 턴은 빈 배열이 정답이고, 빈 문자열은 불일치다.
  지시로는 지어내기를 못 막고 인용은 셀 수 있다는 것이 채택 이유다.

## 범위 제외

| 항목 | 이유 |
|---|---|
| 툴콜 트레이스를 이 피드백 입력에 확장 | 트레이스는 탐색 순서 — 결과로 판정하는 원칙과 무관. 방식을 보는 [pattern 피드백](pattern-feedback-design.md)이 대신 싣는다 |
| 트레이스에 피드백 프롬프트 포함 | 트레이스는 코드 생성 루프의 기록이다 |
| FE에 형식 가이드 노출 | 피드백이 형식의 노출 채널이다 |
| 피드백 재생성·이력 | 제출은 1회, 저장분을 그대로 반환하는 현행 계약을 유지 |
| 기존 데이터 마이그레이션 | 턴 피드백 `null`을 그대로 두고 FE가 overall만 렌더 |
| FE 구현 | 이 문서는 백엔드 계약까지 |

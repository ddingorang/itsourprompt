# 턴별 프롬프트 피드백 설계 결정 기록

작성일: 2026-07-30

## 목적

- 제출 시 생성하는 피드백을 어템프트 전체 한 덩어리가 아니라 **턴별**로 나눈다.
- 각 턴의 사용자 프롬프트를 [결과 형식](prompt-format.md)의 6칸으로 **변환 → 대조 → 처방** 한다.
- 두 축을 판정한다. 축 1은 요구가 반영됐는지, 축 2는 방향 결정을 사용자가 했는지 AI에 위임했는지다.

평가 대상은 프롬프트뿐이다. 코드 품질·정답 여부는 판정하지 않는다.

## 응답 봉투

턴 분할만 스키마로 고정하고 내용은 markdown으로 둔다.

```json
{
  "turns": [{ "turn": 1, "feedbackMd": "..." }],
  "overallMd": "..."
}
```

| 선택지 | 평가 |
|---|---|
| **최소 봉투(턴 번호 + markdown) (채택)** | 렌더 단위가 고정되고 내용 형식은 프롬프트만 고쳐 바꿀 수 있다 |
| 축·판정·근거까지 필드로 고정 | 어휘를 바꿀 때마다 스키마·DTO·FE가 함께 움직인다 |
| 전체를 markdown 한 덩어리로 | 턴별 접기·턴 이동 같은 FE 표현이 불가능하다 |

확장은 additive로만 한다 — 필드를 추가하되 기존 필드의 의미·형태는 바꾸지 않고, FE는 모르는 키를 무시한다.

**구버전 공존**: 이 변경 전에 제출된 어템프트는 턴 피드백이 `null`이다. 그런 어템프트는 `turns`가
빈 배열로 나가고 FE는 `overallMd`만 렌더한다. 기존 데이터를 마이그레이션하지 않는다.

## 턴별 피드백 3단 구조

| 단계 | 하는 일 |
|---|---|
| ① 변환 | 사용자 프롬프트를 6칸에 재배치한다. 사용자 표현을 인용하고, 정보가 없는 칸은 `(없음)`으로 표시한다 |
| ② 대조 | 빈 칸·모호한 칸이 실제 변경 파일에 남긴 흔적을 연결하고 두 축을 판정한다 |
| ③ 처방 | 개선된 프롬프트 예시를 준다. 턴 1은 6칸 전체, 턴 2+는 `직전 결과` + 바뀐 칸만 |

변환 단계가 먼저인 이유: 사용자는 결과 형식을 모르는 상태로 프롬프트를 쓴다. 자기 문장이 6칸에
어떻게 배치되는지 먼저 보여야 어느 칸이 비어 있었다는 지적이 성립한다. 피드백 자체가 형식의
노출 채널이다 — 형식 가이드를 별도로 읽히지 않는다.

## 축 1 — 요구 반영

**판정 경계**: 프롬프트 문장과 그 턴의 변경 파일 쌍만 본다. 코드 품질 평가, 문제 명세 기준의
정답 채점, 해답 코드 제공은 금지다.

| 판정 | 의미 | 이어지는 코칭 |
|---|---|---|
| `반영` | 프롬프트가 요구한 변경이 결과에 있다 | — |
| `부분 반영` | 일부만 반영됐다 | 빠진 부분이 어느 칸의 공백에서 왔는지 |
| `미반영(프롬프트 원인)` | 프롬프트가 전달하지 못했다 | 어느 칸이 부족했는지 연결 |
| `미반영(실행 실패)` | 전달은 됐지만 AI가 못 했다 | 다음 턴 재지시 방법 |

프롬프트 원인과 실행 실패를 나눈 이유: 사용자가 고칠 수 있는 것만 프롬프트 코칭으로 돌린다.
실행 실패를 프롬프트 탓으로 돌리면 고칠 수 없는 지적이 된다.

## 축 2 — 방향 소유

명세에 답이 없는 결정을 사용자가 지정했는지, AI에 맡겼는지를 본다. 3단 관찰로 판정한다.

1. **결정 지점 식별** — 변경 파일에서 명세가 정하지 않은 선택이 이뤄진 지점을 찾는다.
2. **프롬프트 대조** — 그 지점에 대한 방향 표현이 프롬프트에 있었는지 본다.
3. **다음 턴 반응** — 사용자가 그 선택을 확인했는지 다음 턴 프롬프트에서 읽는다.

| 판정 | 조건 |
|---|---|
| `지정` | 프롬프트가 방향을 정했다 |
| `위임-검토 흔적 있음` | 프롬프트엔 없었지만 다음 턴에서 그 선택을 확인한 흔적이 있다 |
| `위임-무언급` | 프롬프트에도 없고 다음 턴에서도 언급이 없다 |
| `확인 불가` | 판단 근거가 없다. **마지막 턴은 항상 이 값** |

마지막 턴이 `확인 불가`로 고정되는 이유: 검토 흔적의 증거가 다음 턴 프롬프트인데, 마지막 턴에는
다음 턴이 없다. 없는 증거로 위임을 단정하지 않는다.

어조는 조건부로 한다 — "의도였다면 명시했어야", "확인했다면 `직전 결과`에 남겼어야". 사용자의
의도를 단정하지 않는다.

## 판정 어휘 통제

두 축의 판정값은 위 표의 문자열만 쓴다. 6칸 라벨(목표/작업 대상/요구사항/제약/완료 조건/검증)과
후속 턴의 `직전 결과`도 변형을 금지한다. 어휘가 흔들리면 사용자가 피드백과 형식 문서를 연결할 수
없고, 같은 상태에 다른 이름이 붙는다.

## 남용 방지

프롬프트 코칭이 "칸을 채우라"는 잔소리로 퇴화하는 것을 막는다.

- **칸 존재가 아니라 정보 존재로 판정한다** — 산문 한 줄에 수정 범위가 담겨 있으면 제약은 충족이다.
- **정보량 0인 칸은 인정하지 않는다** — `제약: 기존 기능 유지`류.
- **소형 수정의 한 줄 프롬프트는 정상으로 인정한다** — 빈 칸을 나열해 지적하지 않는다.
- **명세에 없는 구현 방식·라이브러리 지시는 과잉지정으로 지적한다**.

## overall

세션 전체 패턴만 다룬다: 위임 반복, `직전 결과` 습관, 턴에 따른 프롬프트 진화. 여기에 잘한 점과
최우선 개선 1~2개를 붙인다. 개선된 프롬프트 예시는 턴별 처방에만 두고 overall에는 두지 않는다.

## 생성 시점: 제출 시 일괄 (유지)

| 선택지 | 평가 |
|---|---|
| **제출 시 전체 턴을 한 번에 (채택)** | 축 2가 "다음 턴 반응"을 증거로 쓰므로 턴 N 판정에 턴 N+1이 필요하다 |
| 턴마다 즉시 생성 | 턴 N 시점에 다음 턴이 없어 축 2가 전부 `확인 불가`가 된다 |

턴마다 생성하면 피드백이 다음 턴 프롬프트에 섞여 들어가 평가 대상이 오염되는 문제도 있다.

## 채택 기술

- **json_schema 구조화 출력** — 봉투를 파싱 실패 없이 받는다. Spring AI가 `strict=true`를 고정하므로
  모든 object는 `additionalProperties: false`이고 모든 속성이 `required`에 있어야 한다.
- **완성 토큰을 턴 수에 비례** — 턴별 3단 구조라 출력 길이가 턴 수에 따라 늘어난다. 고정값이면
  긴 세션에서 잘린다.
- **구분자 격리** — 신뢰할 수 없는 데이터(명세·스켈레톤·사용자 프롬프트·AI 요약·변경 파일)를 각각
  태그로 감싸 지시와 구분한다. 사용자 프롬프트가 시스템 지시를 덮어쓰는 것을 막는다.
- **턴 수 검증** — 응답의 턴 피드백 개수가 어템프트 턴 수와 다르면 실패로 처리한다. 턴과 피드백의
  1:1 대응이 봉투의 유일한 계약이다.

## 범위 제외

| 항목 | 이유 |
|---|---|
| 툴콜 트레이스를 피드백 입력에 확장 | 트레이스는 탐색 순서 — 결과로 판정하는 원칙과 무관 |
| 트레이스에 피드백 프롬프트 포함 | 트레이스는 코드 생성 루프의 기록이다 |
| FE에 형식 가이드 노출 | 피드백이 형식의 노출 채널이다 |
| 피드백 재생성·이력 | 제출은 1회, 저장분을 그대로 반환하는 현행 계약을 유지 |
| 기존 데이터 마이그레이션 | 턴 피드백 `null`을 그대로 두고 FE가 overall만 렌더 |
| FE 구현 | 이 문서는 백엔드 계약까지 |

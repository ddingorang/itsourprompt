# 코드 생성 툴콜링 전환 설계 결정 기록

작성일: 2026-07-29

## 목적

- LLM이 툴콜링(`list_files`, `read_file`, `edit_file`)으로 문제 프로젝트의 파일 구조를 직접 탐색·이해하고, 구현 방식을 생각해 제시하며 코드를 수정한다.
- `edit_file`만 허용한다. 새 파일 생성은 불가능하다.
- 멀티턴 두 층위를 모두 지원한다.
  - 어템프트 단위 멀티턴: 프롬프트를 여러 번 이어서 보낸다.
  - 1 프롬프트 내 멀티턴: 모델이 툴콜을 여러 라운드 반복하는 에이전틱 루프.

## 현재 상태와 범위 소거

### 이미 구현되어 있어 범위에서 제외

| 항목 | 위치 |
|---|---|
| 어템프트 단위 멀티턴 (턴 저장 + 히스토리 재생) | `Attempt.turns`, `CodeGenerationPrompts.messages()` |
| 어템프트 생명주기: start / addTurn / submit, idempotency, 피드백 | `AttemptService`, `IdempotencyGuard` 등 |
| 턴별 변경 파일 diff 계산 | `FileChanges.diff` |

### 대체 대상

단발 호출 방식 코드 생성: 전체 파일을 프롬프트에 넣고 JSON 스키마(`response_format`)로
전체 파일 스냅샷을 되받는 구조 (`CodeGenerationSchema`, `GeneratedCodeParser`).

### 신규 구현

- 툴 3개 정의와 요청 단위 작업본 상태
- 1 프롬프트 내 수동 에이전틱 루프
- 툴콜 트레이스 저장·노출

## 사전 조사 사실

- Spring AI 2.0에서 툴 실행 루프가 1.x의 ChatModel 내부에서 `ToolCallingAdvisor`(ChatClient advisor)로 이동했다.
- 프레임워크 루프에는 반복 상한 옵션이 없다 (`ToolCallingChatOptions`, advisor Builder 모두 부재).
- 1.x의 `internalToolExecutionEnabled` 옵션은 삭제됐다. `ChatModel`을 직접 호출하면 툴 자동 실행이 없으므로, `tool_calls` 응답을 받아 `ToolCallingManager.executeToolCalls()`로 직접 도는 것이 2.0의 수동 경로다.

## 결정 기록

### 1. 초기 컨텍스트: 명세 + 사용자 프롬프트만 제공

| 선택지 | 평가 |
|---|---|
| **명세 + 프롬프트만, 파일은 툴로 탐색 (채택)** | 툴 사용이 강제되고 탐색 과정이 관찰 가능. 토큰 절약 |
| 전체 파일 내용을 프롬프트에 포함 | `read_file`이 사실상 죽은 툴이 됨. 과제 취지 훼손 |

파일 트리조차 주지 않는다. 모델이 `list_files`부터 호출한다.

### 2. 툴 셋: `list_files`, `read_file`, `edit_file` 3개

추가 툴 검토 결과:

- `grep`/`search`: 문제 파일이 스켈레톤 수준으로 적어 불필요. 문제가 커지면 추가.
- `create_file`/`delete_file`: 가드레일(파일 셋 고정)이 금지. 제외.

### 3. `edit_file` 편집 방식: 전체 교체

| 선택지 | 평가 |
|---|---|
| **`(path, 새 전체 내용)` 전체 교체 (채택)** | 실패 모드 없음. "새 파일 금지" 검증이 path 존재 확인으로 끝남 |
| `(path, old_string, new_string)` 부분 교체 | 불일치·중복 매치 시 에러 피드백 루프로 라운드 낭비 |
| 라인 범위 교체 | 라인 번호가 어긋나면 조용히 파일 훼손. 최악 |

path가 현재 파일 셋에 없으면 에러를 반환한다 (새 파일 생성 차단).

### 4. 외부 에이전트 도구 vs 직접 구현: 직접 구현

pi, opencode, Claude Agent SDK(JS/Python) 재사용과 비교했다.

| 관점 | 외부 도구 | 직접 구현 (채택) |
|---|---|---|
| 런타임 | Node/Python 사이드카 + IPC, 배포·운영 부담 | 기존 Spring 프로세스 안 |
| 파일 모델 | 실제 파일시스템 전제 — DB 파일을 임시 디렉토리로 내리고 동기화 필요 | DB 파일 셋을 메모리 작업본으로 |
| 툴 제한 | 범용 에이전트를 3개 툴로 울타리 치기 — 보장 어려움 | 툴 3개만 존재, 금지가 코드로 보장 |
| 모델 | Claude Agent SDK는 Anthropic 전용 (우리는 OpenAI) | Spring AI OpenAI 배선 재사용 |
| 동시성 | 요청당 프로세스 spawn | 요청당 상태 객체 |
| 결과 회수 | 에이전트 출력 파싱 필요 | 작업본을 그대로 반환 |

툴콜링 프로토콜과 스키마 생성·인자 파싱은 Spring AI가 제공하므로, 직접 구현의 실제
분량은 툴 3개 + 작업본 상태 + 루프 상한 수준이다. 외부 도구의 강점(bash, 대형 repo
탐색, 검증된 프롬프트)은 이 요구사항에 없다.

### 5. 루프 제어: 수동 루프

| 선택지 | 평가 |
|---|---|
| **`OpenAiChatModel` 직접 호출 + `ToolCallingManager.executeToolCalls()` + 자체 while 루프 (채택)** | 상한·트레이스·라운드 로깅이 평범한 우리 코드 |
| ChatClient + `ToolCallingAdvisor` 자동 루프 | 상한 옵션이 없어 어차피 advisor 서브클래싱 필요 — 학습 비용만 추가 |

### 6. 루프 상한: 10라운드 + 5분 하드 백스톱

라운드 = 모델 호출 1회 (한 라운드에 병렬 툴콜 가능). 전형 시나리오는 5~8라운드.

두 한도는 다른 실패를 막는다:

- **10라운드 (횟수)** = 토큰 비용 보호 + 우아한 마무리. 초과 시 툴을 제거하고 요약을
  한 번 더 요청한 뒤, 그때까지의 편집을 반영해 턴을 저장한다. 히스토리 누적 재전송
  때문에 토큰 비용은 라운드 수에 제곱으로 붙으므로 시간 한도만으로는 못 막는다.
- **5분 (시간)** = 사용자 대기 보호. 초과 시 기존과 동일하게
  `CodeGenerationTimeoutException`으로 하드 실패.

상한을 12가 아닌 10으로 잡은 이유: 라운드당 20~30초를 가정하면 12라운드는 5분을
넘겨 타임아웃이 먼저 터진다 (상한이 죽은 코드가 됨). 10 × 25초 ≈ 4분으로 정상적으로
상한이 먼저 발동한다.

기각한 대안: 라운드 상한 없이 소프트 데드라인(경과 4분)만 두는 방식 — 빠른 퇴화
루프(같은 파일 반복 read)의 비용 폭주를 못 막는다.

### 7. 툴콜 트레이스: 최소 저장 + API 노출

| 선택지 | 평가 |
|---|---|
| **Turn에 최소 트레이스(순서, 툴 이름, path) 저장 + API 응답 노출 (채택)** | 루프가 돈 증거가 밖에서 보임. FE가 "AI가 X 읽고 Y 수정" 표시 가능 |
| 서버 로그만 | 멀티턴 루프가 외부에서 관찰 불가 |
| 인자·결과 본문까지 풀 저장 | 파일 내용 중복 저장 — 용량 낭비 |

### 8. 최종 응답: 일반 텍스트 = `aiSummary`

파일은 `edit_file`이 만든 작업본에서 나오므로 응답에 파일이 필요 없다. 남는 필드가
텍스트 하나뿐이라 JSON 스키마는 포장지다. "어떻게 구현할지 생각하고 제시"도 자유
텍스트가 자연스럽다. `CodeGenerationSchema`, `GeneratedCodeParser`는 삭제한다.

### 9. 무편집 턴: 허용

"구조 설명해줘", "계획만 제시해줘" 같은 프롬프트에서 모델이 `read_file`만 하고 답할
수 있다. 편집 0회면 changes가 빈 턴으로 저장하고 답변은 `aiSummary`에 담긴다. 계획
제시가 일급 시나리오이므로 억지 편집을 강제하지 않는다.

### 10. 어템프트 멀티턴 히스토리: 요약 + 수정 파일 목록

| 선택지 | 평가 |
|---|---|
| **턴별 `userPrompt` + `aiSummary` 재생, assistant 메시지에 수정 파일 목록 한 줄 추가 (채택)** | `Turn.changes`에서 수정 경로를 공짜로 얻음. 불필요한 재탐색 감소 |
| 과거 툴콜·결과까지 전부 재생 | 토큰 폭발 + 옛 read_file 결과가 현재 상태와 모순 |
| 히스토리 없음 | 어템프트 멀티턴 요구를 깸 |

현재 파일 상태의 정본은 항상 툴로 다시 읽는다.

### 11. 파일 삭제: 지원하지 않음

가드레일 취지가 파일 셋 고정(새 파일 금지)이므로 삭제 금지가 쌍으로 맞다. 스켈레톤
문제에서 삭제 시나리오는 사실상 없다. `FileChange.ADDED/DELETED` 타입은 남지만
실제로는 발생하지 않는다. 필요해지면 `delete_file` 툴 추가는 싼 변경이다.

## 파생 구현 사항

- 툴 인자 오류(`edit_file`·`read_file`의 미존재 path)는 예외가 아니라 **에러 문자열을
  툴 결과로 반환**한다. 모델이 자가 수정하며, 해당 라운드도 상한에 카운트된다.
- 요청마다 작업본(파일 맵) 상태 객체를 만들고, 툴은 그것을 닫는(closure)
  `ToolCallback`으로 등록한다 — 동시 요청 격리.
- `CodeGenerator` 포트 반환을 확장한다: 최종 파일 + 요약 + 트레이스. (`GeneratedCode`
  확장 또는 새 결과 레코드 — 구현 시 결정)
- `Turn`에 툴콜 컬렉션 테이블을 추가하고 `AttemptResponse`에 노출한다.
- 프롬프트 캐시 키 `attempt-{id}`는 유지한다. reasoning effort는 low 유지가 원안이었으나,
  실 호출 검증에서 gpt-5.6-luna가 /v1/chat/completions의 함수 툴 + reasoning_effort 병용을
  400으로 거부해 코드 생성 경로는 `none`으로 변경했다 (피드백 경로는 medium 유지).
